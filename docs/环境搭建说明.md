## 一、快速开始（三条命令）

```bash
cd carbon-platform

# 1. Python 环境（必须用 Homebrew Python，原因见 §2.1）
/opt/homebrew/bin/python3 -m venv .venv
export PIP_CONFIG_FILE=$PWD/data-pipeline/pip.conf     # 必须，原因见 §2.2
.venv/bin/python -m pip install -r data-pipeline/requirements.txt

# 2. 生成统一能耗数据集（约 2-3 分钟）
.venv/bin/python data-pipeline/scripts/01_profile_bdg2.py        # 数据测绘，约 1 分钟
.venv/bin/python data-pipeline/scripts/02_build_unified_dataset.py  # 构建数据集，约 2 分钟

# 3. MySQL 数据库（独立实例，端口 3307）
./scripts/mysql.sh init
```

## 二、踩坑记录（重要，避免重复踩）

### 2.1 ⚠️ 不要用 DSH 内置 Python 创建 venv

**现象**：

```
ImportError: dlopen(...numpy/_core/_multiarray_umath.cpython-312-darwin.so, 0x0002):
  code signature ... not valid for use in process:
  mapping process and mapped file (non-platform) have different Team IDs
```

**原因**：macOS 对二进制有代码签名校验。DSH 内置 Python 由特定 Team ID 签名，
而从 PyPI 镜像安装的 C 扩展（numpy / pyarrow 的 `.so`）签名不同，加载时被系统拒绝。
内置 Python 环境与 pip 安装的二进制扩展**不兼容**。

**结论**：
- 数据管道 → 用 `/opt/homebrew/bin/python3 -m venv .venv`（本项目 `.venv`）
- `.venv` 也**不能**用 DSH 内置 Python 运行（内置 Python 的 numpy 2.3.5 与 venv 的 2.5.4 冲突）
- 一句话：**跑数据管道只用 `.venv/bin/python`**

### 2.2 ⚠️ pypi.org 在本机不可达，必须用国内镜像

**现象**：`pip install` 长时间无输出后静默失败，包一个都没装上。

**实测**：

| 源 | 响应 |
|---|---|
| `https://pypi.org/simple/` | 超时（15s 仅下载 778KB / 868KB） |
| `https://pypi.tuna.tsinghua.edu.cn/simple/` | **0.43s** |

**解决**：项目已提供 `data-pipeline/pip.conf`（清华源）。使用前设置：

```bash
export PIP_CONFIG_FILE=$PWD/data-pipeline/pip.conf
```

### 2.3 ⚠️ 本机 `timeout` 命令不存在

macOS 默认不带 GNU `timeout`。脚本中不要使用，改用 `curl --max-time` 或在 Python 中控制。

### 2.4 ⚠️ BDG2 表计数值语义：区间消耗量，不是累计读数

**这是最容易出错、且错了会全盘皆错的一点。**

- BDG2 的 `meter_reading` 是**每小时区间消耗量**（kWh）
- ✅ 统计时段能耗：直接 `SUM()`
- ❌ **禁止** `diff()` 或"本次读数 − 上次读数"

**证据**：`Hog_office_Nia` 冷冻水序列 `44.053 → 44.053 → 44.932 → 43.833 → 44.163`，
数值可升可降，单调递增比例仅 0.484。BDG2 官方 notebook 亦用 `groupby(...).sum()` 做日聚合。

### 2.5 ⚠️ 表计列名就是 building_id，不要做字符串切分

`building_id` 形如 `<站点>_<用途>_<名称>`（如 `Panther_office_Clementine`）。
按 `_` 切分取最后一段会把同站点同用途的建筑**全部合并成一个**。

**验证**：表计列名与 `metadata.building_id` 精确匹配率 100%
（electricity 1578/1578、chilledwater 555/555、water 146/146）。

### 2.6 ⚠️ BDG2 表计并非都可用，必须逐表计校验

实测发现至少三类不可用表计：

| 问题 | 实例 | 处置 |
|---|---|---|
| 覆盖率不足 | `Bobcat_education_Emile` 仅 17.3% | 降为 B 级分摊 |
| 有覆盖无读数 | 覆盖率 99% 但读数恒为 0 | 剔除 |
| 量级失真 | Eagle 冷冻水推算 EUI 达 33 万 kWh/m²·年 | 剔除 |

**校验依据**：用 BDG2 官方 `metadata.eui`（能耗强度）做单位校准——
全电建筑的表计推算 EUI 与官方值比值 1.083，证明电表读数确为 kWh。

## 四、MySQL 环境明细

### 4.1 为什么用独立实例

本机已有 MySQL 8.4 服务运行在 3306（`brew services` 管理），但 **root 密码未知**
（已尝试空密码、root、123456、password、mysql 均失败）。

为了**不改动既有环境**，项目在 `.mysql/` 下自建独立实例：

| 项 | 值 |
|---|---|
| 端口 | **3307**（避开已有的 3306） |
| 数据目录 | `carbon-platform/.mysql/data`（项目内，删除即清理） |
| 账号 | `root` / 空密码 |
| 安装路径 | `/opt/homebrew/opt/mysql@8.4/bin`（不在 PATH 中，需显式导出） |
| 连接串 | `mysql+pymysql://root@127.0.0.1:3307/carbon_energy?charset=utf8mb4` |

### 4.2 生命周期管理

```bash
./scripts/mysql.sh init     # 首次：初始化 + 建库表 + 导入 600 万行
./scripts/mysql.sh start    # 启动
./scripts/mysql.sh stop     # 停止
./scripts/mysql.sh status   # 查看状态与各表行数
./scripts/mysql.sh cli      # 进入 mysql 命令行
./scripts/mysql.sh reset    # 删除数据重新开始
```

### 4.3 若要用你自己的 MySQL

```bash
mysql -u 你的用户 -p < data-pipeline/sql/01_schema.sql
CARBON_MYSQL_URL="mysql+pymysql://用户:密码@主机:3306/carbon_energy?charset=utf8mb4" \
  .venv/bin/python data-pipeline/scripts/07_load_to_mysql.py
```

## 六、常见问题

**Q: 跑 `02_build_unified_dataset.py` 报 `ModuleNotFoundError: No module named 'config'`**
A: 脚本需要 `data-pipeline/src` 在 `sys.path` 中，脚本内已自动处理。
若手动调用，请从 `carbon-platform` 目录执行。

**Q: parquet 写出被跳过，提示 `Unable to find a usable engine`**
A: 用了没有 pyarrow 的解释器。请用 `.venv/bin/python`。

**Q: 数据里 `cop` / `chw_supply_temp_c` 缺失率很高（95.41%）**
A: 这不是错误。这些字段依赖冷冻水计量，而**只有装有可用冷冻水表计的建筑才有值**。
BDG2 中多数园区的冷冻水表计量口径不可用（见 §2.6），已按校验规则剔除。

**Q: `anomaly_flag = -1` 是什么意思**
A: 表示**未评估**。B 级（站点分摊）建筑的电耗是估算值，对其做异常检测无意义，
因此置 -1。统计时须排除（`WHERE anomaly_flag IN (0,1)`）。

**Q: 为什么 `hvac_kwh` 缺失率约 43%**
A: 同上，取决于园区是否有可用的冷冻水/蒸汽/热水表计。这是 BDG2 的客观限制，
不是数据处理缺陷。
