# 碳能智控 · AI 创新点与实施计划

> 本文基于对项目代码与数据库的**实测盘点**（2026-10-31），不含臆测。
> 目的是回答三个问题：现在有什么、还能加什么 AI 能力、怎么落地。

---

## 一、当前功能盘点（实测）

### 1.1 已经真正做完的

| 模块 | 能力 | 实测证据 |
|---|---|---|
| 数据导入 | CSV/Excel 五步向导、AI 字段映射、清洗规则、预览、审计、回滚/追溯 | `data_import_log` 34 条；9 个接口；`FieldMappingPlanner` 接 `LlmClient` |
| 监控看板 | 6 个 KPI、日/月趋势 + 室外温度双轴、园区对比、类型占比 | 截图 + `/energy/overview` |

### 1.2 数据底座（决定能做什么）

| 资产 | 规模 | 可用性 |
|---|---|---|
| 逐小时能耗 | **5,991,840 行** | 实测（BDG2） |
| 建筑维度 | 456 栋 / 18 园区 | 面积 456 全有，EUI 431，评级 419 |
| 异常事件 | 74,597 条 | ⚠️ 处置备注 0 条、类型仅 1 种（能耗偏高） |
| 空气温度 | 逐小时 | 实测，可做温度-能耗建模 |
| COP / 供回水温 / 人员密度 | — | ⚠️ **仿真**，不可当实测讲 |

### 1.3 诚实的"含金量"判断

**已经不算普通管理系统的部分**：3D 园区 + 能效着色、异常归因证据链、AI 工具调用闭环、RAG 专业问答、LLM 报表叙述。

**仍偏"管理系统"的部分**：所有能力都是**被动响应**——用户查什么它答什么，不会主动发现问题、不会预测、不会给方案算收益。

> 一句话：现在的小E 是"会查数的助手"，还不是"会提建议的专家"。

## 二、AI 创新点（按价值/成本排序）

### P1 · 能耗预测与超额预警（Predictive）

**痛点**：现在只能看历史，明天会不会超、什么时候超，没人知道。

**做什么**：预测未来 24h / 7d 逐小时用电，超出历史分位（如 P90）就提前告警。

**数据**：5.99M 逐小时 + 空气温度（温度是最强外生变量）。

**创新点**：从"事后统计"变成"事前预警"；可解释（"预计 14:00 达 182 万 kWh，因气温升至 33℃"）。

**实现要点**（不引重依赖）：
1. 基线模型：`同建筑 × 同星期 × 同时刻` 的历史中位数（seasonal naive），MAPE 通常 8~15%
2. 温度修正：对残差做一元线性回归（`残差 ~ 气温`）
3. 置信区间：取历史同槽位 P10/P90
4. 输出：`{time, predicted, lower, upper, risk}`

**提示词**：
```
你是建筑能耗预测分析师。基于我给的预测数据与历史基线，用中文写 120 字以内的预警解读。
规则：
1. 必须点明建筑名称、预测时段、预测峰值与对应时刻；
2. 只使用我给的数据，不得编造；
3. 若预测未超阈值，直接说"预计平稳"，不要制造焦虑；
4. 给出 1 条可执行动作（如错峰、提前预冷）。
```

**成本**：中（3~5 天）。**这是最值得先做的**——答辩时"能预测"和"只能统计"是两个物种。

---

### P2 · 节能潜力测算（What-if / Prescriptive）

**痛点**：现在给的建议是"建议清洗冷凝器"，但没人知道做了能省多少钱。

**做什么**：给定假设（如"夜间基线降 10%""COP 从 3.4 提到 4.0"），算出年省电量、碳减排、费用。

**数据**：真实用电 + COP + 峰谷电价 + 排放因子 0.5810。

**创新点**：把"建议"变成"可量化的投资回报"，这是运维负责人真正关心的语言。

**实现要点**：
1. 口径固定：`节省电量 = 现状电量 × 调节幅度`（线性假设，必须标注）
2. 分场景：夜间待机、COP 提升、峰谷转移（峰谷电价差）
3. 输出：`{场景, 年省kWh, 年省碳kg, 年省费用元, 假设说明, 置信度}`

**提示词**：
```
你是节能改造测算师。基于我给的真实用电数据与假设参数，输出一段测算说明。
规则：
1. 必须明确写出所用假设（如"夜间基线下降 10%"），假设不得隐去；
2. 每个数字都要能由我给的数据推出，不得自行发挥；
3. 结论分三句：省多少电、减多少碳、省多少钱；
4. 最后一句提示"以上为线性估算，实际需现场核查"。
```

**成本**：低（2~3 天）。**性价比最高**——数据都是现成的，只是没人算过。

---

### P3 · 相似建筑归因（Peer-based Diagnosis）

**痛点**：诊断一栋楼异常，现在只看它自己的历史；但"同类建筑正常时是什么样"更有说服力。

**做什么**：找出同园区/同类型/同面积段的正常建筑，对比它的 COP、夜间基线、EUI，指出"你比同类高 X%"。

**数据**：456 栋画像（面积/EUI/评级）+ 逐小时。

**为什么不做"历史处置案例检索"**：实测 `fact_anomaly_event` 的 `handled=1` 为 **0 条**、`handle_note` 全空、`anomaly_type` 只有 1 种。没有历史处置语料，做不了"上次怎么解决"。

**创新点**：把诊断从"和自己比"升级为"和同类比"，结论更硬。

**提示词**：
```
你是建筑能效对标分析师。基于我给的目标建筑与同类建筑统计，写一段对标结论（150 字内）。
规则：
1. 明确对标口径（同园区/同类型/面积段）；
2. 只说出差距最大的 2 项，不要罗列全部；
3. 数字原样引用，不要换算；
4. 若目标优于同类，要如实说"优于同类"，不要为了给建议而贬低。
```

**成本**：低（2 天）。

---

### P4 · 每日自动巡检简报（Agentic / Proactive）

**痛点**：现在要人去点开页面才发现问题。

**做什么**：每天定时跑一个 Agent：扫全部建筑 → 按风险排序 → 生成一段"今日要关注这 3 栋"的简报，推到看板顶部或消息。

**数据**：异常 + 趋势 + 评级变化。

**创新点**：从"人找问题"变成"系统找人"，这是 Agent 化的关键一步。

**实现要点**：
1. `@Scheduled` 每日 07:00 跑
2. 风险分 = 异常小时权重 + 异常率环比 + COP 下降 + 评级下跌
3. 生成简报（LLM，复用报表的数字校验）
4. 前端看板顶部卡片展示

**提示词**：
```
你是园区运维值班分析师。基于我给的今日巡检数据（异常增加最多的建筑、COP 下降最多的建筑、评级变动），
写一段 200 字以内的值班简报。
规则：
1. 先给一句总体判断（平稳 / 需关注 / 需处置）；
2. 最多点名 3 栋建筑，每栋一句话说明原因与建议动作；
3. 只使用我给的数据；没有异常就说"今日无新增异常"，不要凑；
4. 不要用"非常""极大"这类词。
```

**成本**：中（3~4 天）。

---

### P5 · 跨建筑能效标杆（Benchmarking）

**痛点**：有 431 栋 EUI 数据，但用户不知道"我这栋在同类型里排第几"。

**做什么**：同类型分位数排名 + 差距拆解（面积/使用强度/COP）。

**数据**：`dim_building` 面积、EUI、评级。

**创新点**：把孤立指标变成"位置感"，一眼看出管理水平。

**成本**：低（1~2 天）。

---

### P6（可选）· 碳账本与碳强度

按园区/类型统计碳排、碳强度（kgCO₂/m²）、同比趋势，支撑"双碳"叙事。成本低，但创新度一般。

### P7（可选）· 知识沉淀闭环

运维处理完异常后填一条备注 → 自动切块入 RAG → 下次问答能召回。**前提是先让"处置备注"有数据**（当前为 0）。

## 三、实施计划

| 阶段 | 内容 | 周期 | 产出 |
|---|---|---|---|
| **第一阶段（打地基）** | P2 节能测算 + P5 标杆对比 | 1 周 | 两个"能算钱、能定位"的能力，答辩立刻可用 |
| **第二阶段（上预测）** | P1 能耗预测 + 预警 | 1~1.5 周 | 从"事后"到"事前"，最出彩 |
| **第三阶段（Agent 化）** | P4 每日巡检简报 + P3 相似归因 | 1.5 周 | 从"被动查"到"主动报" |

**排序理由**：P2/P5 数据全现成、改动小、见效快，先把"能算收益"这件事立住；再上预测（需要建模）；最后做 Agent（依赖前两步的结果）。

**统一约束**（沿用现有规范）：
- 所有数字经 `findUnknownNumbers` 校验，不合规回退模板
- 仿真字段（COP/供回温/人员密度）在回答里必须标注"仿真"
- 不新增重型依赖（预测用纯 Java 统计即可）

## 四、现在该怎么改进（按优先级）

| 优先级 | 问题 | 建议 |
|---|---|---|
| **高** | 异常事件 `handled=0`、无处置备注 | 加"处置"功能（标记已处理 + 备注），否则 P7 永远做不了，且"闭环"是假的 |
| **高** | 异常类型只有 1 种（能耗偏高） | 答辩时主动说明数据集限制；或补"能耗偏低/持续运行"的规则生成 |
| **高** | 所有 AI 能力都是被动响应 | 先做 P2（能算钱）+ P1（能预测），观感立刻不同 |
| 中 | 无告警推送 | 加 SSE 或 30s 轮询 + 看板告警条 |
| 中 | 报表只有 API/弹窗，无定时推送 | 加"每日简报"（P4） |
| 低 | 37 栋未评级 | UI 上标注"数据不足，未评级"，不要留空 |
| 低 | 不支持的格式（JSON 导入） | 已确认暂不需要 |

## 五、答辩话术建议

不要说"我们做了个管理系统"，要说：

> "平台把 599 万条逐小时数据变成了三类能力：
> **看得见**（3D + 看板）、**查得准**（AI 工具调用 + RAG）、
> **算得清**（节能测算 + 预测预警）。
> 机器人小E 不是聊天框，它背后是 12 个受控查询工具和 8,931 条知识切片，
> 每个数字都能回溯到 SQL。"

重点是：**数据量 → 能力 → 可验证**，而不是功能列表。
