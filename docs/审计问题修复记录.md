## 追加修复：截图提问改为「真·多模态」

**此前结论有误**。我最初判断「deepseek-chat 不支持图片输入」，未做实测就下了结论。
本轮实测推翻了这个判断：

| 测试 | 结果 |
|---|---|
| `GET /models` | 账号可用模型：`deepseek-flash`、`deepseek-v4-pro` |
| 纯红 64×64 图 → 「什么颜色」 | 回答「红色」✅ |
| 纯蓝 64×64 图 → 「什么颜色」 | 回答「蓝色」✅ |
| 真实看板截图 → 「三栋异常建筑及时长」 | 读出 961 / 909 / 888 小时，与截图内容一致 ✅ |

**改动**：
- `LlmClient.chatWithImage(...)`：新增多模态接口，默认实现退化为纯文本
- `OpenAiCompatibleLlmClient.chatWithImage(...)`：按 OpenAI 兼容格式发送
  `content: [{type:text}, {type:image_url}]`；失败自动降级纯文本
- `ImageContextChatService`：图片转 data URL（宽度 >1600 自动等比缩放），
  与真实数据快照一并交给模型；返回 `imageAnalyzed=true`
- 提示词去掉「不要声称看到图片内容」，改为「只描述截图中确实可见的内容」；
  并要求「截图与数据不一致时以数据为准并指出差异」

**实测**：`imageAnalyzed=true`，7.2s 返回，回答同时引用截图中的数值（961/909/888）
与数据快照（6.14 亿 kWh、61,511 起异常），末尾不再有「无法查看截图」的免责句。

## 追加修复：截图分析「读不到图」的真因

**现象**：模型回答「我无法看到截图内容」，但直接调 API 却能准确读图。

**根因**：`ImageContextChatService.analyze()` 先调 `MultipartFile.transferTo()`
把上传临时文件**移走**，再调 `toDataUrl()` 读同一个文件 —— 此时临时文件已不存在，
`图片转 base64 失败`，dataUrl 为 null，`chatWithImage` 退化成纯文本，
模型自然回答"看不到截图"。**日志里只有一条 WARN，请求仍然 200。**

**修复**：进入方法时 `getBytes()` 一次性读入内存，校验 / 落盘 / 转 base64 全部复用同一份字节。

**顺带修的三处体验问题**：

| 问题 | 修复 |
|---|---|
| 快照只有 11 个总量指标，只能泛泛而谈 | 补环比、逐日序列、峰谷日、最严重的 3 起异常明细 |
| 提示词是固定四段模板，不要求读图 | 改为「先读图 → 再对账 → 再解释 → 最后建议」，并要求逐条列出图中可见数字 |
| 图片问答与文字问答两套历史，追问丢上下文 | `DeepSeekToolCallingService.rememberExchange()` 打通 |

**实测（修复后）**：

- 文字卡片截图（XK-7391 / 42.7% / 17 次 / 丙班）：四项全部正确读出，
  并主动指出「这张图与能耗数据无关」，给出针对告警本身的建议
- 真实看板截图：描述了页面结构 + 三栋异常建筑（81/961、99/909、22/888）
  + 12/25–29 由 133.6 万升至 155.5 万 kWh，并与数据逐项核对确认一致
- 跨模态追问：先传图问「哪栋异常最久」，再用纯文字问「那栋楼用电量」，
  正确调用 `getBuildingEnergySummary(Rat_public_Caroline)` → 1,311,438.8 kWh
