### 1.2 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | Vue 3.5 + TypeScript | 申报表指定 Vue3；TS 提供类型安全，与后端 DTO 一一对应 |
| 构建 | Vite 6 | 冷启动快；原生支持分包与懒加载 |
| UI | Element Plus | 组件完整、中文生态好；表格/表单/步骤条直接满足看板与管理需求 |
| 图表 | ECharts 5 | 赛题推荐的图表库；按需引入控制体积 |
| 3D | Three.js | 申报表要求 3D 园区模型；WebGL 生态最成熟 |
| 后端 | Spring Boot 3.5 + JDK 21 | 申报表要求 Vue3 + Spring Boot；JDK 21 匹配本机环境 |
| ORM | MyBatis-Plus 3.5.9 | 聚合查询需手写 SQL；比 JPA 更贴合报表场景 |
| 鉴权 | Spring Security + JWT（jjwt） | 无状态，便于前后端分离与横向扩展 |
| 数据库 | MySQL 8.4 | 本机已有；分区表与窗口函数满足时序聚合需求 |
| 报表导出 | EasyExcel 4.0 | 流式写出，多 Sheet，避免 POI 直接使用的模板代码 |
| 接口文档 | springdoc-openapi 2.9（OpenAPI 3 + Swagger UI） | **不用 Knife4j**：Knife4j 最新版 4.5.0 捆绑 springdoc 2.3.0，在 Spring Boot 3.5（Spring Framework 6.2）上运行时报 NoSuchMethodError，接口文档实际不可用（已实测踩坑并修复） |
| 数据管道 | Python 3.14 + pandas + pyarrow | 赛题推荐 Python；pandas 处理宽表 unpivot 最高效 |

> **关于若依（RuoYi）**：申报表提及"基于若依框架模块化扩展"。本项目**未直接使用若依**，
> 而是自研轻量脚手架，仅保留项目真正需要的 **RBAC 权限**与**审计留痕**两项能力。
> 理由：① 本机为 JDK 21，若依官方版本基于 Spring Boot 2.x/JDK 8，兼容成本高；
> ② 若依含大量本项目不需要的模块（代码生成、定时任务、多数据源等），裁剪成本高于自研；
> ③ 审计留痕本质是一张 `sys_oper_log` 表 + 一个 AOP 切面，自研约 200 行。
> 该技术决策已记录，可在答辩时说明。

## 二、数据集设计说明

### 2.1 数据集来源与转换链路

**数据源**：[BDG2（Building Data Genome Project 2）](https://github.com/buds-lab/building-data-genome-project-2)
— 开源学术数据集，**CC-BY 4.0** 许可，1636 栋非住宅建筑 / 3053 个表计 / 2016–2017 全年 17544 小时 / 19 个园区。

BDG2 是**宽表**（每列一个表计，时间戳为行索引），且**不直接满足申报表字段要求**，需经转换：

```
BDG2 原始（真实测量）
  metadata.csv   1636 栋建筑属性（类型/面积/楼层/人数…）
  weather.csv    331,166 行站点级天气（干球温度、露点温度…）
  meters/*.csv   8 类表计宽表（电力/冷冻水/蒸汽/热水/燃气/水/光伏/灌溉）
        │
        │  ① 逐表计覆盖率测绘 → 选表配置
        │  ② 宽表 → 长表（unpivot，直接 SUM，**不做 diff**）
        │  ③ 计量口径可信度校验（覆盖率 / 读数有效性 / 能耗强度上限）
        │  ④ 建筑级聚合 + B 级建筑按面积分摊站点剩余量
        │  ⑤ 单位统一（kBtu → kWh ×0.29307107）
        │  ⑥ 推算补全（露点→湿度 / 供回水温度 / 人员密度 / COP）
        │  ⑦ 分层基线-偏差异常标注
        ▼
统一能耗数据集（申报表 4 类核心字段，45 列，5,991,840 行）
```

### 2.2 数据集核心语义（关键，易错）

#### 2.2.1 表计数值是「区间消耗量」而非累计读数

- ✅ 统计时段能耗：**直接 `SUM()`**
- ❌ **禁止** `diff()` 或"本次读数 − 上次读数"

**证据**：`Hog_office_Nia` 冷冻水序列 `44.053 → 44.053 → 44.932 → 43.833 → 44.163`，
数值可升可降，单调递增比例仅 **0.484**。BDG2 官方 notebook 亦采用 `groupby(...).sum()` 做日聚合。
若按累计读数处理，全部统计结果将错误。

#### 2.2.2 数据来源三态标注

| 来源 | 字段 | 说明 |
|---|---|---|
| **实测** | `electricity_kwh`、`hvac_kwh`、`water_m3`、`air_temperature_c`、`area_m2`… | BDG2 原始测量 |
| **推算** | `humidity_pct`（露点→Magnus 公式）、`carbon_kg`、`hvac_electricity_kwh` | 物理公式推导 |
| **仿真** | `chw_supply_temp_c`、`chw_return_temp_c`、`cop`、`occupancy_density` | 规则模型生成，**非实测** |
| **标注** | `anomaly_flag`、`equipment_status`、`severity`、`data_quality_flag` | 算法产出 |

> ⚠️ 对外演示与问答中，仿真字段不得表述为实测值（申报表第 17 条要求）。

#### 2.2.3 数据分级 A / B

| 级别 | 含义 | 可否用于指标评估 |
|---|---|---|
| **A** | 建筑拥有独立电表且读数有效（431 栋） | ✅ 可用于召回率/误报率评估 |
| **B** | 无独立电表，电耗按面积占比分摊（25 栋） | ❌ 仅补覆盖度，`anomaly_flag = -1`（未评估） |

### 2.3 推算与仿真模型

#### 湿度推算（Magnus 公式）

BDG2 只提供露点温度，无相对湿度。按 Magnus 公式推算：

```
饱和水汽压  es(T) = 6.112 · exp(17.67·T / (T + 243.5))   [hPa]
相对湿度    RH    = 100 · es(Td) / es(T)                   [%]
```

#### 空调供回水温度与 COP（仿真）

BDG2 未测量水温与机组 COP，按物理规律建模：

```
供水温度 = 7.0 + 0.08·(T_air − 25) + 1.2·负荷率     clamp [6.0, 12.0] ℃
回水温度 = 供水温度 + ΔT,  ΔT = 2.0 + 3.0·负荷率     clamp [8.0, 18.0] ℃
COP     = 5.2 · f_temp · f_load
          f_temp = 1 − 0.018·max(0, T_air − 25)      （高温衰减）
          f_load = 0.55 + 0.45·min(负荷率, 1.0)      （部分负荷衰减）
          clamp [1.8, 6.5]
```

**验证**：COP 随室外温度呈合理上升趋势（<0℃ 时 2.86 → 28-35℃ 时 4.46），
供回水恒满足"回水 ≥ 供水"（1,127,589 条有效记录**零违例**）。

#### 人员密度（仿真）

优先使用 BDG2 metadata 实测 `occupants`（仅 230/1636 栋有值），缺失时按
**建筑类型 × 人员在室率曲线**生成，人均面积基准按业态取值（教学楼 8 ㎡/人、办公楼 12 ㎡/人…）。

### 2.4 计量口径可信度校验（关键质量保障）

实测发现 BDG2 存在三类不可用表计：

| 问题类型 | 实例 | 判据 | 处置 |
|---|---|---|---|
| 覆盖率不足 | `Bobcat_education_Emile` 仅 17.3% | 覆盖率 < 50% | 降为 B 级分摊 |
| 有覆盖无读数 | 覆盖率 99% 但读数恒为 0 | 中位数 ≤ 0.01 | 整列剔除 |
| 量级失真 | Eagle 冷冻水推算 EUI 达 **331,596** kWh/㎡·年 | 能耗强度 > 类型上限 | 整列剔除 |

**单位校准依据**：用 BDG2 官方 `metadata.eui` 与表计推算值对比 ——
全电建筑比值 **1.083**、全体中位 **0.935**（官方含燃气，故表计值略低），
证明电表读数确为 kWh，无需换算。

**能耗强度上限**（kWh/㎡·年，依据实测分布与官方 eui 校准）：
electricity 1500、chilledwater/steam/hotwater/gas 600、water 1500 m³/㎡·年。

### 3.2 在线查询数据流

```
前端请求 → Vite 代理 → Spring Security（JWT 校验）→ Controller
  → Service（参数校验：时间跨度上限 366 天 / 小时粒度限单建筑）
  → Mapper（路由到合适的表）
        ├─ 明细查询（单建筑时序） → fact_energy_hourly（命中 idx_building_ts）
```

**预聚合表设计（性能关键）**

跨大量行的聚合查询无法靠索引解决（索引加速定位，无法避免逐行聚合）。
实测：按建筑类型分组统计，查事实表 **3.458s**（❌ 超过 2s 验收线）→
查 `agg_building_monthly` **0.041s**（✅），提升 **84 倍**。

规范：**看板与报表一律查预聚合表，MCP 明细查询工具才查事实表**。

## 五、算法/模型设计

### 5.1 分层基线-偏差诊断算法

申报表表述为"分层基线-偏差诊断算法实现『数据采集-异常识别-原因诊断-运维建议』闭环"。

#### 5.1.1 异常识别

**为什么不能用固定 z 倍数阈值**

建筑逐时电耗近似**对数正态分布，右尾很重**。用 MAD 估计尺度 σ 时，σ 远小于真实尾部宽度，
导致固定 3σ 在**完全正常**的数据上就有 **12.2%** 的点超阈值，无法满足"误报率 ≤ 10%"。

**算法**

```
① 分层基线：按「星期几 × 小时」分组（168 个槽位），
   取前 N 周同槽位历史值的【中位数】作为该时刻的期望水平
   —— 消除日周期与周周期成分，残差中不再混入周期波动

② 分位数阈值：取同槽位历史【残差的 q 分位数】作为异常判定上限
   —— 误报率由分位数直接控制，与分布形状无关

③ 显著性下限（关键补充）：
   要求被标记读数同时超过该建筑自身的 P75 分位
   —— 抑制"近零负荷建筑偶尔用电即被判异常"的系统性误报

④ 判定：
   残差 > max(分位数阈值, P75 − 基线)  →  能耗异常
```

**参数确定过程（数据驱动，非拍脑袋）**

| 现象 | 实测 | 结论 |
|---|---|---|
| 实际超限率随回看窗口变化 | 2 周 34.8% → 4 周 23.0% → 13 周 11.2% → 26 周 8.1% → **52 周 6.7%**（理论 1%） | 建筑能耗具强季节性（非平稳），历史窗口必须足够长 |
| 近零基线建筑异常率异常偏高 | 基线 <1 kWh/h 的建筑异常率 **12.98%**，其他区间 6.1%~7.4% | 需引入显著性下限 |

二维扫描（`06_sweep_baseline.py`）结果：**回看 52 周 + 分位数 0.99** 达到
召回率 98.76% / 误报率 6.70%；加入显著性下限后进一步优化至 **98.68% / 3.29%**。

#### 5.1.2 原因诊断（归因）

基于「**异常时段 vs 正常时段**」的客观对比自动生成归因假设，只输出**有数据支撑**的结论：

| 归因规则 | 判据 | 置信度 |
|---|---|---|
| 室外温度升高 | 异常时段均温比正常时段高 ≥ 3.0℃ | 高 |
| 人员在室率上升 | 人员密度相对增幅 ≥ 20% | 中 |
| 机组能效下降 | 平均 COP 低 ≥ 0.3 | 高 |
| 供回水温差偏小（小温差大流量） | 平均温差 < 4.0℃ | 中 |
| 原因待查 | 上述因素均无显著差异 | 低 |

每条结论输出：`cause`（原因）、`confidence`（置信度）、`evidence`（数据证据）、
`suggestion`（处置建议）、`needsManualReview: true`（需人工复核）。

#### 5.1.3 运维建议

基于建筑能效画像（COP、温差、供水温度、异常率、夜间基载）触发 5 类建议规则：

| 规则 | 触发条件 | 量化依据 |
|---|---|---|
| 提升机组能效 | 平均 COP < 3.8 | 冷凝温度每降低 1℃，离心机 COP 约提升 2%~3% |
| 改善小温差大流量 | 平均供回水温差 < 5.0℃ | 温差由 2.5℃ 提升到 5℃ 可使冷冻水输配能耗下降约 40%（相似定律） |
| 优化供水温度设定 | 平均供水温度 < 7.5℃ | 供水温度每提高 1℃，机组 COP 约提升 2%~4% |
| 治理高频异常时段 | 异常率 > 5% | 已识别异常可在事件表中追溯并登记处理结论 |
| 核查夜间基载偏高 | 夜间电耗 > 日间 60% | 夜间基载是公共建筑最易忽视也最易见效的节能点 |

### 5.2 异常识别指标评测方法

**方法**：注入式评测（fault injection）—— 在真实 BDG2 电耗时序的已知位置注入已知类型的异常，
再用检测算法识别，对比注入位置与检出结果。这是异常检测领域的标准评估方法，**完全可复现**（固定随机种子）。

| 注入类型 | 形态 | 期望被哪类判定检出 |
|---|---|---|
| 能耗尖峰（spike） | 3 小时抬升至基线 + 4~9σ | `anomaly_flag`（能耗异常） |
| 表计卡死（frozen） | 连续 30 小时数值冻结 | `data_quality_flag`（数据质量缺陷） |
| 数据缺失（dropout） | 连续 26 小时置空 | `data_quality_flag` |

**关键设计**：能耗异常与数据质量缺陷**分开评估**。表计卡死是采集侧问题，
若把它们计入能耗异常，会凭空制造数万条"误报"，使误报率指标失真。

**结果**（60 栋 A 级建筑，13,140 小时，注入 1,440 + 3,360 + 1,440 个样本）：

| 类别 | 召回率 | 误报率 | 目标 |
|---|---|---|---|
| 能耗异常识别 | **98.68%** | **3.29%** | ≥90% / ≤10% ✅ |
| 数据质量缺陷识别 | **97.67%** | **1.37%** | ≥90% / ≤10% ✅ |

### 5.3 能耗评级算法

按建筑类型**内部分位数法**分档 A-E（同业态横向对标，避免不同业态直接比较）：
以同类型建筑的能耗强度（kWh/㎡·年）分位数切分，≤20 分位为 A，以此类推。

## 八、安全设计

| 项 | 措施 |
|---|---|
| 认证 | JWT 无状态（HS384，默认 8 小时有效期），密钥支持环境变量覆盖 |
| 授权 | RBAC 三角色（admin/operator/viewer）+ 方法级鉴权 + 前端按钮级权限标识 |
| 防用户名枚举 | 用户名不存在与密码错误返回**同一错误码**（1001） |
| 密码存储 | BCrypt 加密；由代码现场生成密文，不在仓库硬编码哈希 |
| SQL 注入 | 全部使用参数化查询；时段分组的 SQL 表达式由**服务端白名单**生成，不接受用户直接输入 |
| 上传安全 | 仅允许 CSV/XLSX/XLS；`fileId` 做路径穿越校验（拒绝含 `/` 与 `..`）；单文件上限 100MB、单次导入上限 20 万行 |
| 审计 | 所有写操作与敏感查询经 `@OperLog` 记录操作人/参数/耗时/异常 |
| 密钥管理 | `.gitignore` 排除 `*.env`、`application-local.yml`、`*-secret.yml` |

## 十、与 AI 模块的集成设计

### 10.1 分工边界

| | 角色 A（全栈） | 角色 B（AI/算法） |
|---|---|---|
| 技术栈 | Vue3 + Spring Boot 3 + MySQL | Python + FastAPI + RagFlow + 轻量 LLM |
| 交付 | 数据集、数据库、后端、前端、系统集成 | MCP 7 类工具、RAG 知识库、小E 助手、诊断算法 |

### 10.2 解耦设计（Mock 优先）

```java
public interface AiServiceClient {
    ChatResponse chat(ChatRequest req);
    Map<String, Object> diagnose(DiagnoseRequest req);
    Map<String, Object> generateReport(ReportRequest req);
    Map<String, Object> listTools();
    Map<String, Object> health();
}
// MockAiServiceClient —— 由后端真实统计能力驱动，不依赖外部服务
// HttpAiServiceClient —— 调用角色 B 的 FastAPI 服务
// 切换：carbon.ai.mode = mock | http
```

**Mock 不是返回假数据**，而是用真实的后端统计能力组装回答：意图识别 → 调统计服务 →
生成带数据证据、MCP 工具链、RAG 引用占位、置信度、耗时的完整响应。
这样在前端与问答链路可完整联调的同时，**切换真实服务的成本为零**（改一行配置）。

### 10.3 容错

AI 服务不可用时**不抛异常给前端**，而是返回结构化降级响应
（`ok: false` + 中文提示"AI 服务暂不可用，您仍可使用能耗查询、统计分析与报表导出等基础功能"），
保证"演示过程中无崩溃"（申报表系统稳定性要求）。
