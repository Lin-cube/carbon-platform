## 一、导入的数据怎么用？（覆盖 还是 追加）

### 1.1 写入语义：按「建筑 + 时刻」覆盖

**结论：只覆盖同一栋楼、同一小时的记录；其它时间、其它建筑的历史数据完全不受影响。**

| 操作 | 结果 |
|---|---|
| 导入 2016-01 ~ 2016-12（库里已有同名同时间数据） | **覆盖**这些 (建筑, 时刻) 的记录，记录数不变 |
| 导入 2017-01 ~ 2017-06（库里没有这段） | **追加**，记录数增加 |
| 导入时某栋楼是新的 | 自动登记到建筑维表，建筑列表可见 |
| 同一次文件内出现重复行（同楼同小时） | 按「按建筑+时间去重」跳过重复，只入第一条 |

**实测验证**（同一文件连续导入 3 次）：

```
第 1 次: 成功 3 行, 覆盖历史 3 条
第 2 次: 成功 3 行, 覆盖历史 3 条
第 3 次: 成功 3 行, 覆盖历史 3 条

库中结果：每对 (建筑, 时刻) 始终只有 1 条，电量值不变
```

> ⚠️ **这个覆盖语义是本次修复的**。修复前 `(building_id, ts)` 上只有普通索引，
> 重复导入会**无脑追加**，同一行变成 3 条，SUM 统计翻 3 倍，异常检测与预聚合表全部失真。
> 现在导入前会先按 (建筑, 时刻) 删除已有记录再插入，保证幂等。
> 界面上会显示「覆盖历史 N 条」，N > 0 说明确实替换了旧数据。

### 1.2 数据进了库，怎么在系统里看到

导入完成后，数据会同时落到三处，对应三条使用路径：

| 落点 | 作用 | 在哪里看 |
|---|---|---|
| `fact_energy_hourly`（事实表） | 逐小时明细数据 | **能耗查询**页面按建筑+时间查 |
| `dim_building`（建筑维表） | 建筑档案（自动登记新建筑） | **能耗查询**的建筑下拉框、**3D 园区**、看板筛选 |
| `data_import_log`（审计表） | 导入批次留痕 | **数据导入**页面第 5 步「审计留痕」 |

**注意**：导入的数据**不会自动参与异常检测与预聚合**。原因：

- **异常检测**需要 52 周历史基线。新导入的建筑历史不足，无法判定异常，
  因此 `anomaly_flag = -1`（未评估），这是设计如此，不是 Bug。
- **预聚合表**（`agg_building_daily` 等）是离线批处理的产物。
  导入新数据后，看板的**日/月趋势聚合**不会立即包含这些数据，需要重建预聚合：

```bash
cd <项目根目录>
# 重建预聚合表（约 1~2 分钟）
.venv/bin/python data-pipeline/scripts/07_load_to_mysql.py --rebuild-agg
```

> 如果你只是导入少量数据做验证，可以跳过重建；如果导入的是完整时间段需要出报表，就要重建。

### 1.3 数据质量的三道关卡

导入时数据会经过检查，任何一道不通过都会跳过该行并在界面列出原因：

1. **必填字段**：`building_id`、`timestamp` 必须有值。缺了整行跳过。
2. **物理合理性**：负数能耗按清洗规则剔除（可在第 3 步关闭该规则）。
3. **文件内去重**：同楼同小时只保留第一条。

界面的「字段解析成功数」表格显示每个字段的成功行数与覆盖率。
覆盖率 = 成功行数 ÷ 源数据总行数，所以跳过 2/5 行时所有字段都显示 60%，这是正常的。

### 2.3 几个关键选型理由

| 决策 | 理由 |
|---|---|
| **不用若依（RuoYi）** | 若依官方版基于 Spring Boot 2.x / JDK 8，与本机 JDK 21 兼容成本高；其代码生成、定时任务、多数据源本项目用不到。自研只需 RBAC + 审计两张表 + 一个切面（约 200 行），更快 |
| **MyBatis-Plus 而非 JPA** | 本项目大量复杂聚合查询（报表场景），手写 SQL 更可控；MyBatis-Plus 也是国内使用率第一 |
| **不用 Knife4j 用 springdoc** | Knife4j 4.5.0（最新）捆绑 springdoc 2.3.0，在 Spring Boot 3.5 上报 `NoSuchMethodError`，接口文档实际不可用（已实测踩坑）。springdoc 2.9 官方适配 |
| **RAG 自建而非 RAGFlow** | 语料已是 8,805 条结构化问答对，RAGFlow 最强的 PDF 解析能力用不上；且 RAGFlow 需 Docker + ≥4GB 内存 |
| **不用 Redis** | 见 §4 |

## 四、看板卡顿：为什么不需要 Redis

### 4.1 实测定位

看板卡顿的根因**只有一个接口**，我逐项测了时间：

| 接口 | 优化前 | 瓶颈来源 |
|---|---|---|
| `/api/system/overview` | **1824 ms** | `COUNT(*) fact_energy_hourly` 单项 **426 ms** |
| `/api/energy/dimensions` | 7 ms | — |
| `/api/energy/sites` | 7 ms | — |
| `/api/analytics/period-summary` | 147 ms | — |
| `/api/energy/breakdown` | 243 ms | — |
| `/api/analytics/anomaly` | 259 ms | — |

单项拆解（在 MySQL 里直接计时）：

```
COUNT(*) fact_energy_hourly        426 ms   ← 唯一瓶颈
MIN(ts) fact_energy_hourly         0.28 ms
MAX(ts) fact_energy_hourly         0.20 ms
COUNT(*) fact_anomaly_event          4 ms
information_schema 估算行数          2.9 ms
```

**为什么 COUNT(*) 慢**：InnoDB 没有保存精确行数，`COUNT(*)` 必须扫描索引。
600 万行扫描一次约 400ms，无论加什么索引都无法更快。

### 4.2 已实施的修复

给 `/api/system/overview` 加了**进程内缓存**（`AtomicReference` + 60 秒 TTL），
并在导入完成后**主动失效**缓存。

实测效果：

```
第 1 次（冷启动，真实 COUNT）: 477 ms
第 2 次（命中缓存）:             8 ms
第 3 次:                         8 ms
第 4 次:                         8 ms
```

**看板首屏从 1824ms 降到 2ms 量级。**

### 4.3 为什么不用 Redis

| 维度 | Redis | 进程内缓存（已采用） |
|---|---|---|
| 效果 | 命中 ~1ms | 命中 ~8ms |
| 额外进程 | 需再跑一个 Redis（约 50-100MB 内存） | 无 |
| 运维成本 | 需配置启动、持久化、监控 | 无 |
| 适用前提 | **多实例共享**缓存 / 需跨重启持久化 / 分布式锁 | 单实例、数据变更可感知 |

本项目：**单实例部署、数据只在导入时变化、导入后能主动失效缓存**。
Redis 的核心价值（多实例共享、跨进程一致性）在这里完全用不上，
加它只会多一个要维护的进程。

### 4.4 什么时候才该上 Redis

如果出现以下任一情况，再考虑 Redis 是合理的：

1. 后端**部署多个实例**（负载均衡），需要共享缓存与会话；
2. 缓存内容**重启后仍需保留**（如外部 API 的昂贵结果）；
3. 需要**分布式锁**（如多实例下的定时任务互斥）；
4. 需要**限流计数器**（跨实例的 QPS 控制）。

### 4.5 如果还觉得卡，正确的排查顺序

1. **先看是哪个接口慢**，别猜。用浏览器 F12 → Network 面板，按 Time 排序。
2. 单个接口慢 → 看 SQL 执行计划（`EXPLAIN`），确认是否走了索引。
3. 跨行聚合慢 → 用预聚合表，不要靠加索引或加缓存掩盖。
4. **前端渲染慢** → 看是不是图表数据点过多（本项目已按需引入 ECharts 并做了分包）。
5. 最后才考虑加缓存；加缓存前先问「数据变化时能不能正确失效」。

#### 调试后端（断点）

后端用 Maven 启动时默认不带调试端口。两种做法：

**做法一：VSCode 调试配置**（推荐）

新建 `.vscode/launch.json`：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "java",
      "name": "调试后端",
      "request": "launch",
      "mainClass": "com.carbon.platform.CarbonPlatformApplication",
      "projectName": "carbon-platform-backend",
      "env": {
        "CARBON_AI_MODE": "hybrid",
        "CARBON_LLM_PROVIDER": "deepseek",
        "CARBON_LLM_KEY": "从 secrets/local.env 复制过来（不要提交此文件）"
      }
    },
    {
      "type": "chrome",
      "name": "调试前端",
      "request": "launch",
      "url": "http://127.0.0.1:5173",
      "webRoot": "${workspaceFolder}/frontend/src"
    }
  ]
}
```

> ⚠️ `launch.json` 里不要写死密钥。更安全的做法是装 `dotenv` 插件，
> 或把 `secrets/local.env` 的内容手动 export 到 VSCode 终端后再启动。

**做法二：附加调试**（先启动再连）

```bash

  -Dspring-boot.run.jvmArguments="-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005"
```

### 5.4 ⚠️ 一个必须知道的编译陷阱

**改后端代码后，必须先把旧进程停掉再编译。** 否则会出现：

```
java.lang.Error: Unresolved compilation problem
```

原因：`mvn compile` 会覆写 `target/classes` 里的 `.class` 文件，
而正在运行的 JVM 还在用这些 class。两者交错会留下「半新半旧」的类，
JVM 加载时报「未解析的编译问题」。这个错误**不会在 Maven 输出里报错**
（`BUILD SUCCESS` 照常显示），只在启动时暴露，很容易误判为代码写错了。

**正确顺序**：

```bash
cd <项目根目录>

# 1. 先停后端（含 launchctl 托管的实例）
launchctl remove carbon-backend 2>/dev/null
pkill -f "spring-boot:run" 2>/dev/null
sleep 3

# 2. clean 编译（clean 是必须的，增量编译不够）
cd backend && mvn -s ../scripts/maven-settings.xml clean compile

# 3. 再启动
cd .. && launchctl submit -l carbon-backend \
  -o "$PWD/.logs/backend.log" -e "$PWD/.logs/backend.err.log" \
  -- "$PWD/.logs/run-backend.sh"
```

> 如果在 IDE 里直接点 Debug 运行，IDEA 会先编译再启动，不存在这个问题。
> 这个陷阱主要出现在「命令行编译 + launchctl 常驻」的组合下。

### 5.5 推荐的工作流

```
1. 启动基础设施（数据库必须常驻）
   ./scripts/start-all.sh daemon      ← launchctl 托管，关终端不停止

2. 在 IDE 里改代码
   · 后端：IDEA 打开 backend/pom.xml，改完直接 Debug 运行
   · 前端：VSCode 打开根目录，pnpm run dev 有热更新
   · Python：VSCode 选 .venv 解释器

3. 改完后验证
   cd frontend && pnpm run build      ← 类型检查（别只用 build:only）
   cd backend && mvn -s ../scripts/maven-settings.xml compile

4. 停止
   ./scripts/start-all.sh stop
```

> **关键提醒**：日常开发时如果自己用 IDE 启动后端（占用 8080），
> 就要先停掉 `launchctl` 托管的那个，否则端口冲突：
> ```bash
> launchctl remove carbon-backend
> ```
