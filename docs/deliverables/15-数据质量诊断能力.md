# 数据质量诊断能力说明

> 对应需求：**给缺失时间或单位不一致的数据，检查诊断依据。**
> 本文记录实测发现的问题、修复内容，以及当前能诊断出哪些数据质量问题。

---

## 一、结论先说

| 能力 | 修复前 | **修复后** |
|---|---|---|
| 缺失时间 | ✅ 报「时间格式无法识别」 | ✅ 保持 |
| 时间格式不规范（斜杠/无秒/紧凑/中文） | ⚠️ 部分支持 | ✅ 支持 17 种格式 |
| **紧凑日期被误判** | ❌ `2018050106` → **2033-12-13** | ✅ → 2018-05-01 06:00 |
| **单位不一致（同列混用 kWh/MWh）** | ❌ **完全不检测** | ✅ 相差 300 倍即告警并跳过 |
| 数值缺失 | ⚠️ 静默跳过，无说明 | ✅ 说明原因 |
| 重复行 | ⚠️ 静默跳过 | ✅ 说明「同一建筑同一时刻」 |
| 负值 | ✅ 报「能耗为负值」 | ✅ 保持 |
| 建筑编号为空 | ✅ 报「建筑编号为空」 | ✅ 保持 |

**修复前如果用一份单位混杂的数据导入，系统会静默接受 1000 倍的误差** —— 后续统计、异常检测、能耗评级全部失真，且没有任何提示。这是本次修复的核心。

## 三、三个修复的技术细节

### 修复 1：单位不一致检测

**原理**：预扫描整份文件，算出每个数值列的**中位数**；主循环里若某值与中位数相差超过 **300 倍**，判定为单位混用。

**为什么用中位数而不是平均值**：中位数对极端值不敏感，不会被少数 MWh 行拉偏（而极端值正是要检测的对象）。

**为什么阈值取 300**：kWh 与 MWh 恰好相差 1000 倍，300 能稳定捕获；而同一栋楼逐小时电量一般不会相差 300 倍，不会误伤正常波动。

**处理方式**：跳过该行并给出诊断，**不猜测换算系数**（强行乘 1000 可能制造假数据）。

**可关闭**：`cleanRules.unitConsistencyCheck = false`。

### 修复 2：时间解析顺序

**问题代码**（修复前）：

```java
// 先判 10 位数字 → 当 Unix 秒
if (s.matches("^\\d{10}$")) {
    return LocalDateTime.ofEpochSecond(Long.parseLong(s), 0, ...);
}
// 之后才尝试具体格式
for (DateTimeFormatter f : DATE_FORMATS) { ... }
```

`2018050106` 是 10 位数字，直接落进 epoch 分支 → 2033 年。

**修复后**：

```java
// ① 先按 17 种具体格式尝试（含紧凑与中文写法）
for (DateTimeFormatter f : DATE_FORMATS) {
    LocalDateTime t = LocalDateTime.parse(s, f);
    if (inReasonableRange(t)) return t;    // 年份必须在 2000~2100
}
// ② 最后才当 Unix 时间戳
if (s.matches("^\\d{13}$")) { ... }   // 毫秒
if (s.matches("^\\d{10}$")) { ... }   // 秒
```

**双重保险**：
1. 顺序调整 —— 先格式后时间戳；
2. 年份范围校验 —— 即使误判也被拦下（`2018050106` 若被当 epoch 得到 2033 年，仍在 2000~2100 内… 所以真正起作用的是顺序调整；范围校验拦的是更离谱的误判，如 `1525104000` 当日期会得到 1525 年）。

### 修复 3：跳过行的诊断说明

原实现：

```java
if ("drop".equalsIgnoreCase(ms) && elec == null) {
    skipped++;
    continue;              // ← 静默跳过，用户不知道原因
}
```

修复后：

```java
if ("drop".equalsIgnoreCase(ms) && elec == null) {
    skipped++;
    addError(result, rowNum, "electricity_kwh",
            "电力能耗缺失，按「缺失值策略=剔除」跳过该行", rawValue);
    continue;
}
```

重复行同样补上「与前面行重复（同一建筑同一时刻）」。

## 四、支持的时间格式

| 类型 | 格式示例 |
|---|---|
| ISO 标准 | `2018-05-01 00:00:00`、`2018-05-01T00:00:00` |
| 省略秒 | `2018-05-01 05:00` |
| 斜杠分隔 | `2018/05/01 04:00:00`、`2018/05/01`、`2018/5/1` |
| **紧凑格式** | `2018050106`、`20180501 0600`、`201805010600`、`20180501` |
| **中文格式** | `2018年5月1日7时`、`2018年5月1日 7时`、`2018年5月1日` |
| 仅日期 | `2018-05-01` |
| Unix 时间戳 | 10 位秒、13 位毫秒 |

## 六、当前仍未覆盖的数据质量问题

如实列出，避免以为"全能"：

| 问题类型 | 现状 | 说明 |
|---|---|---|
| 表计卡死（连续读数不变） | ❌ 导入时不检测 | 数据管道层有检测（`data_quality_flag`），但导入路径未接入 |
| 时间戳重复但数值不同 | ⚠️ 按去重跳过后者 | 不判断哪个更可信，直接保留第一条 |
| 数值超出物理可能范围 | ❌ 未检测 | 如单栋楼单小时耗电超过变压器容量 |
| 时区不一致 | ❌ 未检测 | 统一按 Asia/Shanghai 处理 |
| 建筑编号格式不合约定 | ⚠️ 仅警告 | 不强制 `Site_type_Name` 格式 |
| 字段整体缺失（整列为空） | ✅ 上传时告警 | 列画像阶段能识别「空列」 |

**下一步可做**：把数据管道里已有的「表计卡死检测」（连续 24 小时读数不变）接入导入流程，在预览阶段就提示。

## 七、一句话总结

> **修复前，单位错误会静默通过；修复后，每一行没进来的数据都有原因。**
>
> 诊断依据现在是**可追溯的**：第几行、哪个字段、原值多少、为什么被拒绝、可能的原因是什么。
> 这比"导入成功 N 行"更有价值——数据治理的关键不是收下数据，而是**说清哪些没被收下、为什么**。
