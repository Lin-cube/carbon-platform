## 一、文档说明

### 1.1 编写目的

本手册面向碳能智控运维平台的**实际使用者**，说明系统的安装启动方法、8 个功能页面的操作步骤、数据导入流程，以及数据口径与常见故障处理。阅读本手册后，一名不具备编程背景的建筑能源管理人员应能够独立完成：

## 二、系统简介

### 2.1 系统是什么

碳能智控运维平台是一套面向**园区级建筑能耗**的监控、统计、诊断与数据治理系统。它把来自建筑电表、水表、冷热量表的逐小时能耗数据统一接入数据库，提供可视化看板、多维查询统计、异常识别与 AI 问答诊断能力，帮助运维人员回答三个问题：

1. **现在用了多少能？**（看板、3D 园区）
2. **用在哪里、和谁比偏高？**（能耗查询、统计分析）
3. **哪里不正常、为什么、怎么办？**（异常诊断、小E 助手）

### 2.2 三项核心能力

| # | 能力 | 载体 |
|---|---|---|
| ① | **能耗数据导入与治理** | 数据导入页五步向导（数据源选择 → 字段映射 → 清洗规则 → 预览导入 → 审计留痕） |
| ② | **实时监控与可视化看板** | 监控看板（6 张 KPI 卡 + 6 类图表）、3D 园区（Three.js 楼栋着色与拾取）、建筑级状态与评级 |
| ③ | **AI 智慧问答与诊断** | 小E 助手（自然语言问答）、异常诊断页（归因证据链 + 优化建议）、MCP 7 类数据查询工具 |

### 2.3 适用对象

- 高校／园区后勤与能源管理岗位：查看各楼栋用电、碳排放与异常情况；
- 物业与机电运维班组：定位异常建筑、获取排查方向与优化措施；
- 节能改造项目组：获取分时段用电结构、峰谷特征与能效（COP）分析；
- 数据管理员：批量导入外部能耗台账并留存审计记录。

### 2.4 数据基础

| 项目 | 数值 |
|---|---|
| 记录数 | **5,991,840** 条（小时级） |
| 建筑数 | **456** 栋（A 级独立计量 **431** 栋 ／ B 级站点分摊 **25** 栋） |
| 园区数 | **18** 个 |
| 时间范围 | 2016-01-01 00:00 ～ 2017-07-01 11:00 |
| 数据粒度 | 小时级（hourly） |
| 字段数 | 45 个 |
| 数据源 | BDG2 开源数据集（CC-BY 4.0，需署名） |

### 2.5 系统边界（本轮不做的功能）

以下内容**不在**本系统范围内，遇到相关需求请勿在系统内寻找入口：

- 移动端 APP；
- BACnet／Modbus 等楼宇协议的实时直连采集（数据通过文件导入或数据管道入库）；
- 跨园区能耗对标排名；
- 碳交易与碳资产管理、能耗计费出账；
- 能耗预测模型平台（系统提供历史统计与异常识别，不做未来预测）。

## 三、运行环境与安装部署

### 3.1 环境要求

| 组件 | 版本要求 | 用途 |
|---|---|---|
| 操作系统 | macOS（Apple Silicon 已验证） | 开发与演示环境 |
| JDK | **21**（Temurin） | 后端 Spring Boot 3.5 |
| Maven | 3.x | 后端构建（使用项目内阿里云镜像配置） |
| Node.js | **24.21.0** | 前端构建 |
| pnpm | **11.19.0** | 前端包管理 |
| Python | **3.14**（Homebrew：`/opt/homebrew/bin/python3`） | 数据管道 |
| MySQL | **8.4**（`/opt/homebrew/opt/mysql@8.4/bin`） | 数据库（项目独立实例） |
| 浏览器 | Chrome／Edge 最新版（需支持 WebGL） | 3D 园区页面 |

⚠️ **不要用 DSH 内置 Python 创建虚拟环境**：macOS 代码签名校验会导致 numpy／pyarrow 的 C 扩展加载失败。数据管道一律使用项目内 `.venv/bin/python`。

### 3.2 一键启动（推荐）

系统提供一键启动脚本，按顺序拉起 MySQL、后端、前端三个服务。

```bash
cd carbon-platform

# 前台启动：MySQL + 后端 + 前端；按 Ctrl+C 结束本次会话
./scripts/start-all.sh

# 后台启动：日志写入 .logs/，命令立即返回
./scripts/start-all.sh -d

# 查看三个服务的运行状态与访问地址
./scripts/start-all.sh status

# 停止全部服务（含 MySQL）
./scripts/start-all.sh stop
```

脚本行为说明：

| 步骤 | 脚本动作 |
|---|---|
| [1/3] MySQL | 检测 3307 端口；未运行则调用 `./scripts/mysql.sh start` |
| [2/3] 后端 | 检测 8080 端口；未运行则在 `backend/` 下执行 `mvn -s scripts/maven-settings.xml -B spring-boot:run` |
| [3/3] 前端 | 检测 5173 端口；未运行则在 `frontend/` 下执行 `pnpm run dev` |
| 就绪等待 | 每个端口最多等待 40 次 × 2 秒 = 80 秒，超时会提示查看日志 |

后台启动后日志位置：

```bash
tail -f .logs/backend.log     # 后端起不来时第一时间看这里
tail -f .logs/frontend.log    # 前端（Vite）日志
```

💡 `start-all.sh` 采用"端口已在运行则跳过"的策略，重复执行不会重复启动服务，可以放心用来"补齐"某个没起来的组件。

### 3.3 分别手动启动各组件

需要单独调试某个组件时，可按以下顺序手动启动。

**① MySQL（项目独立实例，端口 3307）**

```bash
./scripts/mysql.sh init      # 首次部署：初始化数据目录 + 建库表 + 导入约 600 万行（需数分钟）
./scripts/mysql.sh start     # 启动
./scripts/mysql.sh status    # 查看状态与各表约行数
./scripts/mysql.sh cli       # 进入 mysql 命令行（可直接执行 SQL）
./scripts/mysql.sh stop      # 停止
./scripts/mysql.sh reset     # 危险：删除 .mysql/ 数据目录后重新开始
```

**② 后端（端口 8080）**

```bash
cd backend
mvn -s ../scripts/maven-settings.xml -B spring-boot:run
```

`-s ../scripts/maven-settings.xml` 指定阿里云 Maven 镜像；首次执行需下载依赖，耗时较长。

**③ 前端（端口 5173）**

```bash
cd frontend
pnpm install     # 首次使用必须执行
pnpm run dev
```

前端开发服务器会把 `/api` 请求反向代理到后端 8080，因此浏览器只需访问 5173 即可。

**④ AI 助手服务（可选，端口 8000）**

后端默认以**本地联调模式**运行（`carbon.ai.mode=mock`），不需要额外的 Python 服务即可使用小E 助手。当接入独立的 RAGFlow／FastAPI 服务后，通过配置切换：

```bash
# 方式一：启动前设置环境变量
export CARBON_AI_MODE=http
export CARBON_AI_BASE_URL=http://127.0.0.1:8000

# 方式二：修改 backend/src/main/resources/application.yml 中的 carbon.ai.mode
```

### 3.4 依赖安装

```bash
# 前端依赖
cd frontend && pnpm install && cd ..

# Python 数据管道依赖（必须使用国内镜像，pypi.org 在本机不可达）
/opt/homebrew/bin/python3 -m venv .venv
export PIP_CONFIG_FILE=$PWD/data-pipeline/pip.conf
.venv/bin/python -m pip install -r data-pipeline/requirements.txt

# 验证安装
.venv/bin/python -c "import pandas,numpy,pyarrow,scipy,fastapi,sqlalchemy; print('OK')"
```

⚠️ `export PIP_CONFIG_FILE=$PWD/data-pipeline/pip.conf` **必须执行**（清华源）。不设置时 `pip install` 会长时间无输出后静默失败，包一个都装不上。

### 3.5 启动自检：如何确认每个组件都起来了

| 检查项 | 命令 | 期望结果 |
|---|---|---|
| 三个端口 | `./scripts/start-all.sh status` | 三行均显示 ✅ |
| MySQL | `./scripts/mysql.sh status` | `✅ 运行中 (端口 3307)` 并列出各表行数 |
| 后端健康检查 | `curl --max-time 5 http://127.0.0.1:8080/api/system/health` | 返回统一信封 JSON，`"code":200`，`data.status` 为 `UP` |
| 后端接口文档 | 浏览器打开 `http://127.0.0.1:8080/swagger-ui/index.html` | 显示 Swagger UI 接口文档页（30 个接口） |
| 前端 | 浏览器打开 `http://127.0.0.1:5173` | 显示登录页 |
| AI 助手 | `curl --max-time 5 http://127.0.0.1:8080/api/ai/health` | 返回统一信封，`data.status` 为 `UP`、`data.mode` 为 `mock` 或 `http` |
| 端口占用排查 | `lsof -nP -iTCP:8080 -sTCP:LISTEN` | 列出占用进程（无输出表示端口空闲） |

⚠️ **本机没有 GNU `timeout` 命令**，脚本与自检中请使用 `curl --max-time N` 限制超时时长。

### 3.6 停止与重启

```bash
./scripts/start-all.sh stop          # 一键停止全部（含 MySQL）
./scripts/mysql.sh stop              # 只停 MySQL

# 只重启后端（例如改了 Java 代码）
pkill -f "spring-boot:run" && ./scripts/start-all.sh -d
```

### 3.7 首次部署的数据准备（可选）

若数据库中还没有数据，需先执行数据管道生成数据集并导入。执行顺序如下（均从 `carbon-platform` 目录执行）：

```bash
.venv/bin/python data-pipeline/scripts/01_profile_bdg2.py            # 数据测绘，约 1 分钟
.venv/bin/python data-pipeline/scripts/02_build_unified_dataset.py   # 构建统一数据集，约 2 分钟
.venv/bin/python data-pipeline/scripts/03_make_data_dictionary.py    # 生成数据字典，约 5 秒
.venv/bin/python data-pipeline/scripts/04_eval_anomaly.py            # 异常识别评测，约 2 分钟
.venv/bin/python data-pipeline/scripts/07_load_to_mysql.py           # 导入 MySQL，约 3 分钟
```

或直接使用 `./scripts/mysql.sh init`（内部会自动执行建表与导入）。

## 四、快速上手（5 分钟）

本节给出一条最短动线：**登录 → 看看板 → 问小E**。

### 第 1 步：打开系统

在浏览器地址栏输入：

```
http://127.0.0.1:5173
```

页面左侧显示平台介绍，右侧是登录卡片。若打不开，请先执行 `./scripts/start-all.sh status` 确认前端 5173 是否在运行。

### 第 2 步：登录

1. 在登录卡片的 **演示账号（点击填充）** 分隔线下，点击标签 **管理员：admin / admin123**（点击后用户名与密码自动填入）；
2. 点击 **登录** 按钮；
3. 出现"登录成功"提示后，系统自动跳转到 **监控看板**。

> 也可以手工输入用户名 `admin`、密码 `admin123`，然后点击 **登录**。

### 第 3 步：看一眼监控看板

进入看板后，自上而下依次是：

1. **筛选栏**：园区（默认"全部园区"）、时间范围（默认 2016-01-01 ～ 2016-12-31）、粒度（**日**／**月**）、**刷新**、**导出报表**；
2. **6 张 KPI 卡**：总用电量、空调系统能耗、碳排放量、能耗异常率、建筑／园区、平均 COP；
3. **能耗趋势与室外温度** 折线图；
4. **园区能耗对比**、**建筑类型能耗结构**；
5. **分时用电占比（尖峰平谷）**、**异常事件趋势**；
6. **建筑能耗评级分布**、**异常小时数 TOP 建筑** 表格。

左侧导航栏可切换到其余 6 个业务页面；顶栏右侧显示 **AI 服务** 状态指示灯（绿色可用／红色不可用）、**数据 N 行** 标签；点击右上角用户名可展开 **账号信息** 与 **退出登录**。

### 第 4 步（可选）：进 3D 园区转一圈

1. 点击左侧导航 **3D 园区**；
2. 在左上角面板的 **园区** 下拉中选择一个园区（如 `Hog`）；
3. 鼠标 **左键拖拽旋转** 视角，**滚轮缩放**；
4. **单击任意楼栋**，右侧弹出该楼栋详情，点击 **查看异常诊断** 可直接跳转到异常诊断页。

### 第 5 步：问小E 一个问题

1. 点击左侧导航 **小E 助手**；
2. 顶部状态条显示 **AI 服务可用** 与 **模式 mock** 标签（本地联调模式，属正常状态）；
3. 点击 **示例问题** 中的任一标签（例如 `2016年有哪些能耗异常？`），问题会自动填入输入框；
4. 按 **Enter** 键或点击 **发送**；
5. 回答气泡中会显示答案正文、**调用工具** 标签、可展开的 **数据证据** 与 **知识库引用**，底部显示 **置信度**、**耗时**、**数据来源**。

### 5 分钟动线小结

| 时间 | 动作 | 预期看到 |

| 0:00 | 打开 `http://127.0.0.1:5173` | 登录页 |

| 4:30 | 进入 **统计分析 → 异常分析** | 异常率、异常事件数与 TOP 建筑 |

## 五、功能操作说明

系统共 8 个页面：登录、监控看板、3D 园区、能耗查询、统计分析、异常诊断、小E 助手、数据导入。左侧导航栏列出后 7 个业务页面。

> 💡 **全局筛选共享**：园区与时间范围在多页面之间共享（默认 `2016-01-01 ～ 2016-12-31`）。在任一页面修改后，切换到其他页面会沿用该条件。

---

### 5.1 登录页

**功能说明**
系统入口。采用 JWT 无状态认证，登录后令牌保存在浏览器本地，过期或失效会自动跳回本页。

**操作步骤**

1. 打开 `http://127.0.0.1:5173`；
2. 输入 **用户名** 与 **密码**（也可点击下方演示账号标签一键填充）；
3. 点击 **登录**，或在输入框内直接按 **Enter**；
4. 登录成功后跳转到 **监控看板**；若此前访问其他页面被拦截，会跳回原页面。

**结果解读**

- 成功：右上角出现"登录成功"提示并进入看板；
- 失败：页面弹出错误提示（用户名不存在与密码错误返回同一提示，这是防止账号枚举的安全设计，并非系统故障）。

**注意事项**

- 演示账号（点击填充）区域列出三个账号及其角色，见 [附录 A](#附录-a演示账号与权限)；
- 若登录后立刻被弹回登录页，说明令牌无效或后端重启导致会话失效，重新登录即可；
- 令牌存储在浏览器 `localStorage` 的 `carbon_token` 键中，清除浏览器数据即退出登录。

---

### 5.2 监控看板（/dashboard）

**功能说明**
系统的总览页面，用 6 张 KPI 卡回答"总体用了多少能、异常有多严重"，用 6 类图表展示趋势、结构、分时与评级分布。

**操作步骤**

1. 在筛选栏选择 **园区**（默认"全部园区"，下拉项显示"园区名（栋数）"）；
2. 选择 **时间范围**（日期区间选择器，含 **开始**、**结束** 两个占位）；
3. 选择粒度：**日** 或 **月**（仅影响趋势图的时间粒度）；
4. 点击 **刷新** 重新加载全部指标与图表；
5. 点击 **导出报表** 下载 Excel 报表。

**结果解读**

| 界面元素 | 含义 |
|---|---|
| **总用电量** | 所选范围与园区的用电量合计（kWh），卡片副标题显示 `区间 起止日期` |
| **空调系统能耗** | 空调系统能耗（kWh），副标题 `占用电 x%` 为空调能耗占用电的比例 |
| **碳排放量** | 按 **0.5810 kgCO₂/kWh** 排放因子折算的碳排（kgCO₂） |
| **能耗异常率** | 异常小时 ÷ 评估小时 × 100%，副标题显示异常小时数 |
| **建筑 / 园区** | 覆盖的建筑栋数与园区个数 |
| **平均 COP** | 仅统计**含冷冻水计量**的建筑；无此类建筑时显示 `--` |
| **能耗趋势与室外温度** | 用电量（左轴 kWh）与平均室外温度（右轴 ℃）双轴曲线 |
| **园区能耗对比** | 各园区能耗横向对比 |
| **建筑类型能耗结构** | 按建筑类型（教学楼、办公楼等）的能耗构成 |
| **分时用电占比（尖峰平谷）** | 尖峰／高峰／平段／低谷四个时段的电量占比 |
| **异常事件趋势** | 按时间统计的异常事件数 |
| **建筑能耗评级分布** | A／B／C／D／E 各评级的建筑数量 |
| **异常小时数 TOP 建筑** | 异常小时最多的建筑列表，含 **类型**、**异常小时**、**峰值偏离**（超过 100% 时标红） |

图表标题右侧的彩色徽章表示数据来源：**实测**（绿）、**推算**（黄）、**仿真**（蓝紫）、**算法标注**（粉）。含义见[第七章](#七数据说明与口径)。

**注意事项**

- 图表右上角的徽章是数据可信度提示，**"算法标注"与"推算"结果不能当作实测值对外引用**；
- 时间范围上限为 **366 天**，超出会报错，请缩小范围（见 [8.6](#86-查询报时间跨度过大)）；
- 建筑能耗评级分布由建筑维表统计得出（当前取建筑列表中的部分样本），用于看趋势，不作为逐栋评级的唯一依据；单栋评级请在 3D 园区或能耗查询页查看；
- 导出报表为 Excel 文件，文件名形如 `碳能智控_能耗报表_2016-01-01_2016-12-31.xlsx`，含 5 个工作表：**概览**、**时段汇总**、**分时占比**、**异常分析**、**异常建筑排名**。

### 5.3 3D 园区（/campus3d）

**功能说明**
用三维楼栋模型直观展示园区用能状况：楼栋**颜色**表示能耗水平，楼栋**高度**表示规模，点击楼栋查看明细。

**鼠标操作**

| 操作 | 效果 |
|---|---|
| **左键拖拽** | 旋转视角（环绕园区） |
| **滚轮** | 缩放（拉近／拉远） |
| **右键拖拽** | 平移场景 |
| **单击楼栋** | 选中该楼栋，右侧弹出详情面板 |

画面中的**粒子流**表示用能强度，粒子越密集表示该楼栋用能越强。左侧面板底部也有同样的操作提示。

**操作步骤**

1. 进入 **3D 园区** 页面，等待"正在构建 3D 场景…"消失；
2. 在左上角 **园区** 下拉框中选择园区（选项显示"园区名（栋数）"）；
3. 选择 **建筑着色** 依据：
   - **能耗评级**：A 优秀（绿）／B 良好（浅绿）／C 一般（黄）／D 较差（橙）／E 差（红）／未评级（灰）；
   - **能耗强度**：低强度（绿）→ 高强度（红）五档；
   - **异常率**：正常（<2%，绿）／轻度（2–5%，黄）／偏高（5–10%，橙）／严重（>10%，红）；
4. 选择 **按高度表示** 依据：**建筑面积** 或 **用电量**；
5. 对照左下角 **图例** 判读颜色含义；
6. 单击目标楼栋，在右侧详情面板查看 **建筑类型**、**建筑面积**、**年用电量**、**能耗强度**、**能耗评级**、**数据分级**、**异常率**；
7. 点击详情面板底部的 **查看异常诊断**，跳转到异常诊断页查看该楼栋的异常事件。

**结果解读**

- 右上角 **园区概览** 面板显示：**建筑数**、**年用电量**（kWh）、**年碳排**（kgCO₂）、**异常建筑**（栋，大于 0 时标黄）、**平均评级**；
- 详情面板中的 **数据分级** 标签：A 级 · 独立计量（绿）／B 级 · 站点分摊（黄），含义见 [7.2](#72-数据分级a-级与-b-级)；
- **能耗强度**（EUI）为 `--` 时，表示该建筑缺少面积数据或年度用电数据，属正常缺失。

**注意事项**

- 3D 页面需要浏览器支持 WebGL，建议使用 Chrome／Edge 最新版并开启硬件加速；
- 楼栋高度是**相对缩放**后的视觉效果，只用于横向比较，不代表真实米数；
- 页面加载一次最多绘制所选园区的 300 栋建筑，园区建筑很多时属正常上限；
- **B 级（站点分摊）建筑的能耗为面积分摊估算值**，其颜色深浅不能作为节能考核依据。

### 5.4 能耗查询（/energy）

**功能说明**
按园区、建筑类型、建筑、时间、粒度、指标等条件自由组合查询，输出趋势曲线、建筑对比与逐栋汇总明细，是日常取数的核心页面。

**操作步骤**

1. 在筛选栏依次设置：
   - **园区**：下拉选择，默认"全部园区"；
   - **建筑类型**：如教学楼、办公楼等（选项显示"类型（数量）"）；
   - **建筑**：支持**多选**，可搜索，默认"全部建筑（可多选）"；
   - **时间范围**：默认 `2016-01-01 ～ 2016-12-31`；
2. 在第二行筛选栏设置：
   - **粒度**：**小时**／**日**／**月**（默认 **日**）；
   - **指标**：**用电量**／**空调能耗**／**用水量**／**碳排**（控制主趋势图绘制哪条曲线）；
   - **仅看异常**：打开后只统计被算法标记为异常的小时；
3. 点击 **查询**；
4. 需要恢复默认条件时点击 **重置**。

**结果解读**

| 界面元素 | 含义 |
|---|---|
| **建筑数** | 本次命中的建筑数量，副标题为查询区间 |
| **总用电量 / 总空调能耗 / 总碳排** | 命中建筑在区间内的合计值 |
| **平均 COP** | 仅对 `copAvg` 有值的建筑求平均，副标题显示"仅含 N 栋有冷冻水计量的建筑" |
| **{指标}趋势** | 主趋势图；命中多栋时**每栋一条曲线，最多绘制 8 栋**，超出部分会在图上方给出提示 |
| **各建筑用电量 TOP 15** | 用电量排名前 15 的建筑柱状图 |
| **汇总明细** | 明细表：建筑编号、建筑类型、区间用电量、空调能耗、碳排(kg)、平均COP、EUI；支持点击列头排序，超过 20 行自动分页 |

**注意事项**

- ⚠️ **小时粒度只允许选择且仅选择 1 栋建筑**。选择多栋后点击 **查询**，会提示"小时粒度数据量过大，请选择且仅选择 1 栋建筑；多建筑对比请改用日或月粒度"；筛选栏也会显示 **小时粒度仅支持单栋建筑** 的黄色标签；
- 趋势图遇到缺失数据点时**折线断开**（不会画成 0），断点通常意味着该建筑无此表计或无数据，属正常现象；
- 明细中的 **平均COP**、**EUI** 显示 `--` 属正常缺失，原因见 [7.3](#73-为什么有些字段是空的)；
- 查询区间不得超过 **366 天**；
- 页面底部出现"当前条件下没有查询到数据，请放宽筛选条件"时，请检查时间范围是否落在 2016-01-01 ～ 2017-07-01 之间。

### 5.5 统计分析（/analytics）

**功能说明**
提供申报表要求的**三类核心统计分析**，分别对应三个页签：**时段汇总**、**COP 计算**、**异常分析**。三个页签共用顶部的 **园区** 与 **时间范围** 筛选，切换页签会自动按当前条件重新加载。

**操作步骤（通用）**

1. 在顶部筛选栏选择 **园区**、**时间范围**；
2. 点击 **刷新** 重新加载当前页签；
3. 点击 **导出报表** 下载 Excel；
4. 点击页签 **时段汇总**／**COP 计算**／**异常分析** 切换分析类型。

#### 5.5.1 页签一：时段汇总

**操作步骤**

1. 切换到 **时段汇总** 页签；
2. 在 **统计周期** 中选择 **年**／**季**／**月**／**周**／**日**（页面显示"共 N 个时段"）；
3. 查看 KPI 卡、分时段图表与明细表。

**结果解读**

| 界面元素 | 含义 |
|---|---|
| **区间总用电量** | 区间合计，副标题为"时段均值" |
| **峰值 / 谷值** | 各时段中的最大／最小值，副标题给出出现的时段（如 `2016-07`） |
| **峰谷差率** | （峰 − 谷）÷ 峰 × 100%，越大说明用电越不均衡 |
| **分时段用电量与室外温度** | 柱线组合图，便于观察温度与用电的相关性 |
| 明细表 | 时段、用电量(kWh)、空调能耗(kWh)、碳排(kg)、平均COP、平均气温(℃)、异常小时、环比(%)（上升标红、下降标绿） |
| **尖峰平谷电量结构** | 四个电价时段的电量占比 |
| **分时电价时段明细** | 时段类型、对应钟点、电量(kWh)、占比(%)、小时均值 |

时段划分规则（分时电价）：

| 时段类型 | 对应钟点 |
|---|---|
| 尖峰 | 10–12 时、14–17 时 |
| 高峰 | 8–9 时、13 时、18–19 时 |
| 平段 | 7 时、20–22 时 |
| 低谷 | 23 时 ～ 次日 6 时 |

**注意事项**

- **平均COP** 与 **平均气温** 显示 `--` 属正常缺失（该时段没有冷冻水计量数据或气温数据）；
- 环比（%）在首个时段为空（没有上一期可比），显示 `--`。

#### 5.5.2 页签二：COP 计算

**操作步骤**

1. 切换到 **COP 计算** 页签；
2. 在 **建筑（必选）** 下拉中选择一栋建筑（支持搜索；界面提示"后端要求必须指定单栋建筑"）；
3. 点击 **计算 COP**（未选择建筑时按钮为禁用状态）；
4. 查看 6 张 KPI 卡、能效评级提示、两张图表。

**结果解读**

| 界面元素 | 含义 |
|---|---|
| **平均 COP** | 区间内机组能效比的平均值 |
| **最高 / 最低 COP** | 区间内小时最大值／最小值 |
| **标准差** | 越小说明机组运行越稳定 |
| **系统能效比** | 制冷量 ÷ 空调总电耗 |
| **平均供回水温差** | 副标题给出平均供水温度与回水温度（℃） |
| **能效评级** | 平均 COP ≥ 4.5 **优秀**；3.8～4.5 **良好**；3.0～3.8 **一般**；< 3.0 **偏低** |
| **COP 随室外温度变化** | 不同室外温度区间的平均 COP |
| **COP 分布直方图** | COP 值的小时数分布 |

⚠️ **"无数据"是数据现状，不是系统故障。** 选择多数建筑时，页面会显示蓝色提示："该建筑在本区间没有可用的冷冻水计量，无法计算 COP"。原因是 BDG2 数据集中只有少数园区安装了计量口径可用的冷冻水表计（**18 个园区中约 5 个能算出 COP**），其余建筑必然返回无数据。想看到完整 COP 分析，请选择有冷水计量的建筑（如 `Hog_office_Sydney`）。

**注意事项**

- 供回水温度、COP、人员密度均为**仿真值**（由规则模型生成，非实测），只能用于横向参考与趋势判断，**不得作为实测数据引用或写入报告结论**；
- COP 图表徽章可能显示"推算"或"仿真"，两者都表示**非实测**，引用时一律须注明来源。

#### 5.5.3 页签三：异常分析

**操作步骤**

1. 切换到 **异常分析** 页签；
2. 阅读顶部黄色提示（能耗异常与数据质量缺陷是两个独立概念）；
3. 查看 KPI 卡、两张图表与 TOP 建筑表格。

**结果解读**

| 界面元素 | 含义 |
|---|---|
| **评估小时数** | 有效数据小时（已剔除数据质量缺陷小时），是异常率的分母 |
| **能耗异常小时数** | 用能显著高于基线的小时数 |
| **异常率** | 异常小时 ÷ 评估小时 × 100% |
| **数据质量缺陷小时** | 表计卡死、数据缺失等采集问题导致的小时数，副标题给出占比 |
| **异常事件数** | 连续异常小时聚合而成的事件个数 |
| **事件平均 / 最长持续** | 事件持续小时的平均值与最大值 |
| **异常类型构成** | 各异常类型的占比 |
| **异常小时与事件数趋势** | 异常的时间分布 |
| **异常小时数 TOP 建筑** | 建筑编号、园区、建筑类型、异常小时、异常率(%)、峰值偏离(%)、主要异常类型 |

⚠️ **"能耗异常"与"数据质量缺陷"不可相加**：前者表示数据可信但用能偏高，需要运维排查；后者是表计或采集问题，不参与能效评价。异常率的分母是评估小时数，缺陷小时已被剔除。

**注意事项**

- 异常统计**只包含 A 级（独立计量）建筑**；B 级分摊建筑的 `anomaly_flag = -1`（未评估），已被排除；
- 异常识别算法的实测指标为：**召回率 98.68%、误报率 3.29%**（评测方法为注入式仿真，详见 `docs/eval/anomaly_eval_report.md`）；
- 算法标注只是**初筛**，最终处置须由运维人员现场复核。

### 5.6 异常诊断（/anomaly）

**功能说明**
列出异常事件清单，并针对具体建筑给出**归因证据链**（异常时段与正常时段对比）和**优化建议**，是"哪里不正常、为什么、怎么办"的落点页面。

**操作步骤**

1. 设置筛选条件：
   - **时间范围**、**园区**、**建筑**；
   - **异常类型**：下拉选择；
   - **严重度**：**高**／**中**／**低**；
   - **最短持续(h)**：只显示持续时长不小于该值的事件（0～720 小时）；
   - **每页条数**：10／20／50／100；
2. 点击 **查询**（需要清空条件时点击 **重置**）；
3. 在 **异常事件清单** 表格中查看事件，列包含：建筑编号、园区、建筑类型、开始时间、持续(h)、异常类型、严重度、峰值、基线、偏离%、操作；
4. 点击任意一行或该行的 **诊断** 按钮，右侧滑出 **异常诊断** 抽屉；
5. 点击 **优化建议** 按钮，滑出 **优化建议** 抽屉；
6. 表格底部使用分页控件翻页。

**结果解读**

**事件清单**

| 列 | 含义 |
|---|---|
| **峰值 / 基线** | 事件期间的峰值能耗与同期基线值（基线 = 按「星期几 × 小时」分组的历史中位数） |
| **偏离%** | （峰值 − 基线）÷ 基线 × 100%，超过 100% 标红加粗 |

**异常诊断抽屉**

- 顶部标签：**存在能耗异常**（红）或 **未检出明显异常**（绿）；同时显示统计区间与建筑；
- **异常时段 / 正常时段对比** 表：时段、小时数、均电耗(kWh)、室外温度(℃)、人员密度(人/100㎡)、COP、温差(℃)；
- **归因分析（证据链）**：每条归因以卡片呈现，包含 **起因**、**置信度** 标签、**需人工复核** 标签（如触发）、**证据**、**建议**；没有明显归因时显示"未发现明显异常归因"；
- **能效画像**：该建筑的多项能效指标描述。

**优化建议抽屉**

- 顶部 **使用须知** 免责说明；
- 每条建议卡片包含：**标题**、**优先级** 标签、**需人工复核** 标签（如触发）、**依据**、**措施**、**原理**；
- 无有效数据时显示"该建筑在查询区间内无有效数据，暂无法给出优化建议"；
- 底部同样给出 **能效画像**。

**注意事项**

- ⚠️ **归因结论必须经人工复核**。诊断面板中供回水温度、人员密度来自仿真／推算链路，系统对存在不确定性的结论会显式标注 **需人工复核**；系统输出**不直接作为最终决策依据**；
- 当前数据集（2016）中 **严重度为「高」的事件数为 0**，选择 **高** 时可能查不到结果，筛选栏已给出提示，这不是系统故障；
- 园区／建筑下拉框是级联的：先选 **园区** 会收窄 **建筑** 的可选项；
- 本页只展示**异常事件**；表计故障等**数据质量缺陷**不在本页展示，其统计见统计分析页的 **异常分析** 页签。

### 5.7 小E 助手（/assistant）

**功能说明**
对话式智能问答。用中文提问，系统自动解析意图、调用后端统计与 MCP 工具读取**真实数据库结果**，并给出答案、工具链、数据证据、引用与置信度。

**操作步骤**

1. 进入 **小E 助手** 页面，观察顶部状态条：
   - 绿色圆点 **AI 服务可用** ／ 红色 **AI 服务不可用**；
   - **模式 mock**（本地联调）或 **模式 http**（已接入外部 AI 服务）标签；
2. 在 **上下文** 区域（可选）设置：
   - **建筑**：下拉选择"不限建筑"或具体建筑；
   - **时间范围**：默认 `2016-01-01 ～ 2016-12-31`；
   - 提示语说明："不选则由后端按问题文本自动解析时间与建筑"；
3. 在输入框中输入问题（也可先点击 **示例问题** 标签自动填入），
   输入框提示为："用中文提问，例如：2016年有哪些能耗异常？"；
4. 按 **Enter** 发送，**Shift+Enter** 换行；或点击 **发送** 按钮；
5. 需要重新开始时点击 **清空对话**。

**内置示例问题**

| 示例问题 | 覆盖能力 |
|---|---|
| `2016年有哪些能耗异常？` | 异常扫描 |
| `统计Eagle园区2016下半年的用电情况` | 时段汇总 |
| `Hog_office_Sydney 的机组能效如何？` | COP 计算 |
| `Hog_office_Sydney 有哪些可落地的优化建议？` | 优化建议 |
| `2016年各园区的碳排放对比情况` | 维度对比 |

**结果解读**

| 气泡内元素 | 含义 |
|---|---|
| **调用工具** | 本次回答实际调用的 MCP 工具标签（如 `scan_anomalies`、`overview_stats`）；成功为绿色，失败为红色 |
| **数据证据（N 项）** | 可展开的键值对，列出回答所依据的真实统计数字（评估小时数、异常率、事件数等） |
| **知识库引用（N 条）** | 可展开的引用来源、页码与摘要片段（RAG 溯源，用于准确率评估） |
| **置信度** | 0～1 的小数，界面按百分比显示 |
| **耗时** | 本次回答的后端处理毫秒数 |
| **数据来源** | 该回答所依据的数据来源类型（实测／推算／仿真／混合） |
| **会话 xxxxxxxx** | 本次会话编号前 8 位，用于问题回溯 |

**关于本地联调模式（mock）**

当状态条显示 **模式 mock** 时，页面会出现蓝色提示说明：

> 该模式下小E 的答案**不是预设话术**：它由后端真实调用 MCP 工具（能耗查询／时段汇总／异常扫描／COP 计算／问题诊断／优化建议）读取数据库统计结果后生成，只是没有经过 RAG 知识库检索与大模型润色。

因此 **mock 模式下回答中的数字与图表页面完全一致、可信**；区别仅在于表达方式未经大模型润色。接入外部 RAGFlow／FastAPI 服务后，把配置项 `carbon.ai.mode` 改为 `http` 即可，本页面无需改动。

**注意事项**

- 提问**越具体越好**：带上建筑编号（如 `Hog_office_Sydney`）与时间范围（如"2016 年下半年"）可显著提升准确度；也可直接在 **上下文** 区域选择建筑与时间；
- 询问 COP 相关问题时**必须指明建筑**。未指定时小E 会反问："COP 分析需要指定具体建筑。请告诉我要查询哪一栋建筑（例如建筑编号）"；
- 回答中的异常结论同样是**算法初筛结果**，系统会在答案中附上"具体处置需运维人员现场复核"的提示；
- 若状态条显示 **AI 服务不可用**，请见 [8.8](#88-ai-助手提示服务不可用)。

### 5.8 数据导入（/import）

**功能说明**
五步向导式数据导入与治理页面，用于把外部能耗台账（CSV／Excel）导入系统，并留下可追溯的审计记录。详细操作见[第六章](#六数据导入操作指南)。

**操作步骤（概览）**

1. 进入 **数据导入** 页面，顶部步骤条显示五个步骤：**数据源选择** → **字段映射** → **清洗规则** → **预览导入** → **审计留痕**；
2. **步骤一 · 选择数据源**：拖拽文件到上传区或点击选择，系统解析后显示行数、列数与数据预览；
3. **步骤二 · 字段映射**：确认或调整系统自动匹配的目标字段；
4. **步骤三 · 清洗规则**：设置去空格、负值、缺失值、前缀、单位、去重规则；
5. **步骤四 · 预览导入**：查看可导入／解析失败／按规则跳过的行数与明细，确认后点击 **确认导入（写入数据库）**；
6. **步骤五 · 审计留痕**：查看导入结果、批次号与历史导入批次，点击 **详情** 查看该批次的字段映射与清洗规则。

**注意事项**

- 支持 **CSV／XLSX／XLS**，CSV 自动识别 **UTF-8 与 GBK** 编码，**单次导入上限 20 万行**；
- **建筑编号** 与 **监测时间** 为必填字段（下拉选项中带 `*` 标记）；
- 导入的数据默认标记为 **B 级（站点分摊）** 且 `anomaly_flag = -1`（未评估），页面会明确提示；
- 全流程会记录到 `data_import_log`（批次号、字段映射、清洗规则、操作人、时间），可随时回溯。

## 六、数据导入操作指南

### 6.1 准备源文件

**支持的格式**：`.csv`、`.xlsx`、`.xls`；CSV 建议保存为 UTF-8（带或不带 BOM 均可），系统会自动识别 UTF-8 与 GBK。

**推荐列名**（系统会自动匹配，中文列名识别率最高）：

| 推荐列名 | 是否必填 | 单位 | 说明 |
|---|---|---|---|
| **建筑编号** | ✅ 必填 | — | 建筑唯一标识；建议带园区前缀，如 `Demo_teaching_A` |
| **监测时间** | ✅ 必填 | `yyyy-MM-dd HH:mm` | 小时级时间戳 |
| 园区编号 | 可选 | — | 不填则由建筑编号的前缀自动推断；仍无则记为 `IMPORTED` |
| 建筑类型 | 可选 | — | 如"教学楼""办公楼" |
| 电力能耗 | 可选 | kWh | 可被识别为 `electricity`／`elec`／`power`／`电量`／`电耗` 等 |
| 空调系统能耗 | 可选 | kWh | 别名：`hvac`／`空调`／`制冷` |
| 水耗 | 可选 | m³ | 别名：`water`／`用水`／`水量` |
| 燃气能耗 | 可选 | kWh | 别名：`gas`／`天然气` |
| 环境温度 | 可选 | ℃ | 别名：`温度`／`室外温度`／`干球温度` |
| 相对湿度 | 可选 | %RH | 别名：`湿度` |
| 空调出水温度 | 可选 | ℃ | 别名：`供水温度`／`冷冻水供水` |
| 空调回水温度 | 可选 | ℃ | 别名：`回水温度`／`冷冻水回水` |
| 人员密度 | 可选 | 人/100㎡ | 别名：`人员`／`人数` |
| 建筑面积 | 可选 | m² | 别名：`面积` |

**源文件示例**（CSV，UTF-8）：

```csv
建筑编号,园区编号,建筑类型,监测时间,电力能耗,空调系统能耗,水耗,环境温度,相对湿度
Demo_teaching_A,Demo,教学楼,2017-01-01 00:00,182.4,45.2,1.8,2.5,58
Demo_teaching_A,Demo,教学楼,2017-01-01 01:00,175.1,44.0,1.7,2.1,59
Demo_teaching_A,Demo,教学楼,2017-01-01 02:00,168.9,43.1,1.7,1.8,60
```

⚠️ **导入前请检查三点**：① 时间列格式统一；② 能耗列不要混入单位文字（如"182.4 kWh"）；③ 同一"建筑 + 时间"不要重复出现（否则请开启去重规则）。

### 6.2 五步向导逐步操作

#### 步骤一 · 数据源选择

1. 进入 **数据导入** 页面；
2. 把文件**拖到上传区**，或点击"**点击选择**"选择文件；
3. 系统立即解析并显示：
   - 绿色提示条：`已解析 <文件名>：N 行数据、M 列`；
   - 黄色警示条（如有）：例如"文件非 UTF-8 编码，已按 GBK 解析"；
   - **数据预览（前 N 行）** 表格；
4. 确认无误后点击 **下一步：字段映射**（未上传文件时该按钮为禁用状态）。

上传区提示语：支持 CSV / XLSX / XLS；CSV 自动识别 UTF-8 与 GBK 编码；单次上限 20 万行。

#### 步骤二 · 字段映射

1. 页面显示蓝色说明："系统已根据列名与数据特征自动匹配目标字段，请确认或调整。标记「必填」的字段必须映射。"；
2. 在映射表中逐列核对：

| 列 | 说明 |
|---|---|
| **源列名** | 你文件中的列名 |
| **推断类型** | **数值**（绿）／**时间**（黄）／**空列**（红）／**文本**（灰） |
| **样例值** | 该列的前几个非空取值 |
| **目标字段** | 下拉选择要映射到的系统字段，留空或选择"忽略该列"表示不导入 |
| **自动匹配** | **高**（≥0.95）／**中**（≥0.70）／**低**（>0）／**未匹配** |
| **匹配依据** | 系统给出该匹配的原因说明 |

3. 确认 **建筑编号** 与 **监测时间** 已映射（显示为 `建筑编号 *`、`监测时间 *`）；
4. 点击 **下一步：清洗规则**（需要回退时点击 **上一步**）。

💡 自动匹配采用"别名包含匹配 + 相似度打分"，常见中英文列名基本无需手工调整；仅当列名非常规时（如"本月抄见电量"）才需要人工指定。

#### 步骤三 · 清洗规则

逐项设置（各项含义见 [6.3](#63-清洗规则逐条说明)），默认值已适合大多数场景：

| 规则项 | 默认值 | 可选项 |
|---|---|---|
| **去除首尾空格** | 开启 | 开关 |
| **剔除负值能耗** | 开启 | 开关 |
| **缺失值处理** | **保留为空** | **保留为空**／**填 0**／**整行剔除** |
| **建筑编号前缀** | 空 | 文本输入，如 `Demo` |
| **电量单位** | **kWh** | **kWh**／**MWh（自动 ×1000）** |
| **去重策略** | **按「建筑+时间」去重（推荐）** | 按「建筑+时间」去重（推荐）／不去重 |

设置完成后点击 **下一步：预览导入**，系统开始试算（按钮显示加载状态）。

#### 步骤四 · 预览导入

⚠️ 本步骤**尚未写入数据库**，可放心反复调整规则。

1. 查看 4 张统计卡：

| 卡片 | 含义 |
|---|---|
| **源数据行数** | 文件总行数 |
| **可导入** | 通过校验、将被写入的行数（绿色） |
| **解析失败** | 因格式或内容错误无法解析的行数（红色） |
| **按规则跳过** | 被清洗规则主动剔除的行数（橙色） |

2. 若 **解析失败** 大于 0，页面出现黄色提示："有 N 行解析失败，请检查下方明细后再决定是否导入"；
3. 查看 **错误 / 跳过明细（最多展示 100 条）** 表格：**行号**、**字段**、**原因**、**原始值**；
4. 查看 **字段解析成功数** 表格：**目标字段**、**成功解析行数**、**覆盖率**（进度条）；
5. 确认无误后点击 **确认导入（写入数据库）**（当 **可导入** 为 0 时按钮禁用）；需要调整时点击 **上一步**。

#### 步骤五 · 审计留痕

1. 页面顶部显示结果卡片：`导入成功` 或 `导入失败`，副标题为 `批次号 xxx · 成功 N 行 · 失败 N 行 · 跳过 N 行`；
2. 阅读蓝色提示：**导入数据默认标记为 B 级（站点分摊）且 anomaly_flag = -1（未评估）**，因其非本系统标准计量口径；如需纳入异常分析请在数据治理流程中另行确认；
3. 在 **历史导入批次（审计留痕）** 表格中查看全部批次：

| 列 | 含义 |
|---|---|
| **批次号** | 系统生成的唯一批次标识，导入追溯的主键 |
| **文件名 / 类型** | 源文件名与文件类型 |
| **总行 / 成功 / 失败** | 该批次的处理结果 |
| **状态** | **成功**（绿）／**预览通过**（蓝）／其他（黄） |
| **操作人 / 时间** | 执行导入的账号与时间 |
| **详情** | 点击后弹出 **导入批次详情** 对话框 |

4. 点击 **详情**，可查看该批次的 **批次号**、**文件名**、**字段映射**（JSON）、**清洗规则**（JSON）、**操作人**、**时间**；
5. 需要再导一批时点击 **再导入一批**，向导回到第一步。

### 6.3 清洗规则逐条说明

| 规则 | 作用 | 建议 |
|---|---|---|
| **去除首尾空格** | 去掉文本字段两端的空格，避免「 建筑A」与「建筑A」被当作两栋不同建筑 | ✅ 保持开启 |
| **剔除负值能耗** | 能耗为负值时整行跳过（负值通常是表计故障或采集异常） | ✅ 保持开启 |
| **缺失值处理 = 保留为空** | 缺失的能耗值保持为空，不参与求和（不会把缺失当 0） | ✅ 默认，最保守、最安全 |
| **缺失值处理 = 填 0** | 把缺失的**电力能耗**填为 0 | ⚠️ 仅在确认"缺失就是没用电"时使用，否则会低估能耗 |
| **缺失值处理 = 整行剔除** | 电力能耗为空的行整行丢弃 | 仅在要求数据完整时使用，会减少导入行数 |
| **建筑编号前缀** | 源数据的建筑编号没有园区前缀时，自动补齐前缀（如填 `Demo`，编号 `teaching_A` 变为 `Demo_teaching_A`） | 按需填写；不填则编号原样保存 |
| **电量单位 = kWh** | 按 kWh 原值保存 | 源数据为 kWh 时使用 |
| **电量单位 = MWh** | 电力能耗与空调能耗自动 **×1000** 换算为 kWh | ⚠️ 源数据为 MWh 时**必须**切换，否则数据会小 1000 倍 |
| **去重 = 按「建筑+时间」去重** | 同一建筑同一时间戳只保留第一条，其余计入"按规则跳过" | ✅ 推荐；可防止重复导入导致能耗翻倍 |
| **去重 = 不去重** | 全部保留 | 仅在确认数据本身无重复时使用 |

### 6.4 完整操作示例

**场景**：某教学楼 2017-01-01 ～ 2017-01-07 的小时级用电台账，共 168 行，列名为"楼号 / 时间 / 用电量"。

| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 | 把 `教学楼A_201701.xlsx` 拖入上传区 | 提示"已解析 …：168 行数据、3 列"，预览表显示前几行 |
| 2 | 进入 **字段映射** | 系统自动把 `楼号` → **建筑编号**、`时间` → **监测时间**、`用电量` → **电力能耗**，自动匹配列显示"高"或"中" |
| 3 | 检查必填项 | `建筑编号 *`、`监测时间 *` 均已映射 |
| 4 | 进入 **清洗规则** | 保持默认：去空格开、剔负值开、缺失保留为空、单位 kWh、按「建筑+时间」去重 |
| 5 | 在 **建筑编号前缀** 填 `Demo` | 楼号 `A101` 将保存为 `Demo_A101` |
| 6 | 点击 **下一步：预览导入** | 源数据行数 168；可导入 168；解析失败 0；按规则跳过 0 |
| 7 | 检查 **字段解析成功数** | `electricity_kwh` 成功 168 行，覆盖率 100% |
| 8 | 点击 **确认导入（写入数据库）** | 进入第五步，显示 `导入成功`，批次号形如 `IMP20170101xxxxxx` |
| 9 | 阅读蓝色提示 | 该批数据标记为 **B 级**、`anomaly_flag = -1`（未评估） |
| 10 | 在 **历史导入批次** 中点击 **详情** | 可看到字段映射 JSON 与清洗规则 JSON，用于复核 |

**异常场景对照**

| 现象 | 含义 | 处理 |
|---|---|---|
| **解析失败** 出现几行，"原因"为时间格式无法解析 | 该行的时间列不是 `yyyy-MM-dd HH:mm` 格式 | 在原文件中修正时间格式后重新上传 |
| **按规则跳过** 数量较大 | 命中了去重或负值规则 | 点击查看 **错误 / 跳过明细** 的"原因"列确认；若为重复数据则属预期 |
| **可导入** 为 0，按钮禁用 | 全部行被跳过或解析失败 | 返回 **上一步** 放宽清洗规则，或检查必填字段映射 |
| 某字段 **覆盖率** 很低 | 该列大部分单元格为空 | 属数据本身缺失，可正常导入，缺的字段在系统中显示 `--` |

### 6.5 审计留痕怎么看

审计信息分两层：

1. **导入批次表**（页面第五步可见）：记录每个批次的批次号、文件名、类型、总行数、成功／失败行数、状态、操作人、时间——用于回答"这批数据是谁、什么时候导进来的"；
2. **批次详情**（点击 **详情**）：额外给出该批次使用的**字段映射**与**清洗规则**原始 JSON——用于回答"这批数据是怎么处理的"。

此外，系统对导入操作本身还有一层**操作日志**（`sys_oper_log`）：记录操作人、参数、结果、耗时与异常，通过注解自动采集，用于安全审计。

### 6.6 导入数据的口径提醒

- 导入数据统一标记为 **B 级（站点分摊）**、`anomaly_flag = -1`（**未评估**）；
- 因此导入的建筑**不会出现在异常统计的分子与分母中**（异常率分母为"评估小时数"）；
- 若需要将导入数据纳入异常分析，需在数据治理流程中另行确认口径后再行处理；
- 导入数据会参与能耗总量、趋势、结构等查询统计。

## 七、数据说明与口径

本章是理解全部页面数字的钥匙。**建议所有使用者至少通读一遍。**

### 7.1 数据来源三态 + 一标注

系统中的每个字段都有明确的来源标签，界面用彩色徽章展示：

| 来源 | 徽章颜色 | 含义 | 典型字段 |
|---|---|---|---|
| **实测** | 绿色 | BDG2 原始测量值，可直接引用 | `electricity_kwh`（电力能耗）、`water_m3`、`air_temperature_c`、`area_m2`、`hvac_kwh` |
| **推算** | 黄色 | 由实测值经物理公式推导 | `humidity_pct`（露点→Magnus 公式）、`carbon_kg`（碳排）、`hvac_electricity_kwh` |
| **仿真** | 蓝紫 | 按规则／统计模型生成，**非实测** | `chw_supply_temp_c`（空调出水温度）、`chw_return_temp_c`（空调回水温度）、`cop`（机组能效比）、`occupancy_density`（人员密度） |
| **标注** | 粉色 | 算法产出 + 规则约束 | `anomaly_flag`、`anomaly_type`、`severity`、`equipment_status`、`data_quality_flag` |

⚠️ **使用红线（务必遵守）**：

1. **空调供回水温度、COP、人员密度是仿真值，不是实测值。** 它们由"室外温度 + 部分负荷率"规则模型生成，用于展示趋势与相对关系，**不得作为实测数据写入报告、论文或对外宣传材料**；
2. **湿度是推算值**（由露点温度经 Magnus 公式换算），引用时应注明"推算"；
3. **碳排放量是推算值**，换算因子为 **0.5810 kgCO₂/kWh**（生态环境部 2023 年全国电网平均排放因子），口径为"外购电 + 空调电耗 + 燃气"；
4. 界面部分 COP 图表徽章显示"推算"、部分显示"仿真"，**两者都表示非实测**，引用时一律须标注来源类型。

### 7.2 数据分级：A 级与 B 级

| 级别 | 定义 | 数量 | 能否用于指标评估 |
|---|---|---|---|
| **A 级** | 建筑拥有**独立电表**，`electricity_kwh` 为表计级实测值 | **431 栋** | ✅ 可参与异常识别等指标评估 |
| **B 级** | 建筑**无独立电表**，电耗由站点剩余量按**建筑面积占比分摊** | **25 栋** | ❌ 仅用于补建筑覆盖度与总量守恒 |

B 级建筑的 `anomaly_flag` 与 `data_quality_flag` 均为 **-1（未评估）**，统计时**必须排除**（`WHERE anomaly_flag IN (0,1)`）。系统已在后端统计中统一处理，因此：

- 异常率、异常事件数、召回率等指标只反映 A 级建筑；
- 看板与查询中的**总量类**指标包含 B 级建筑（用于展示完整覆盖度）；
- 在 3D 园区详情面板中，B 级建筑的 **数据分级** 标签会明确显示"B 级 · 站点分摊"。

### 7.3 为什么有些字段是空的

系统数据来自 BDG2 开源数据集，**缺失是数据源的客观限制，不是系统处理缺陷**。官方数据字典（由实际产出自动生成）给出的缺失率：

| 字段 | 缺失率 | 原因 |
|---|---|---|
| `electricity_kwh` | 3.98% | 电表覆盖最好，少量时段缺抄 |
| `hvac_kwh` | **43.19%** | 取决于园区是否有可用的冷冻水／蒸汽／热水表计 |
| `water_m3` | **80.27%** | BDG2 中水表覆盖极少 |
| `air_temperature_c` | 0.46% | 气象数据基本完整 |
| `humidity_pct` | 0.49% | 由露点推算，覆盖率与气温一致 |
| `cop` / `chw_supply_temp_c` | **95.41%** | **只有装有可用冷冻水表计的建筑才有值**，18 个园区中约 5 个能算出 COP |
| `occupancy_density` | 0.00% | 仿真字段，全量生成 |

> 说明：`cop` 缺失率按全量 5,991,840 行统计为 **95.41%**（A 级口径 96.05%）。
> 原因是 18 个园区中仅 5 个（Cockatoo、Moose、Panther、Hog、Peacock）存在计量口径可用的冷冻水表计，
> 其余园区的冷冻水表经校验判定为量级失真已剔除。因此绝大多数建筑无法计算 COP，这是**数据源客观限制**。

此外还有两类**主动剔除**的表计数据：

| 问题 | 处理 |
|---|---|
| 覆盖率不足（如仅 17.3%） | 降为 B 级分摊 |
| 有覆盖但读数恒为 0 | 剔除 |
| 量级失真（如推算 EUI 达 33 万 kWh/m²·年） | 剔除 |

### 7.4 `--` 是什么意思

界面中的 `--` 统一表示：**该字段在当前查询范围内没有数据**，通常因为该建筑／园区没有对应的计量表计。

| 出现位置 | 含义 |
|---|---|
| 空调能耗 `--` | 该建筑所在园区没有可用的冷热量表计 |
| 平均 COP `--` | 该建筑没有可用的冷冻水计量 |
| 水耗 `--` | 该建筑没有水表 |
| EUI `--` | 缺少建筑面积或无年度用电数据 |
| 环比 `--` | 首个时段没有上一期可比 |
| 层数／建成年份等 | BDG2 元数据本身缺失（楼层缺失约 73%、建成年份缺失约 50%） |

⚠️ **看到 `--` 不要报故障。** 它是"这里本来就没有表计"的诚实表达，而不是系统算不出来。后端特意保留 `null` 而不过滤，就是为了避免调用方误判为"字段不存在"。

### 7.5 能耗异常与数据质量缺陷的区别

这是两个**刻意分开、不可相加**的概念：

| 概念 | 判定依据 | 处置方向 |
|---|---|---|
| **能耗异常** | 数据本身可信，但用能显著高于同期基线（分层基线 + 分位数阈值算法标注） | 需要运维排查 |
| **数据质量缺陷** | 表计卡死（连续 24 小时数值冻结）或数据缺失造成的无效小时 | 采集／表计问题，不参与能效评价 |

异常率的分母是**评估小时数**（有效数据小时），数据质量缺陷小时已从评估基数中剔除。

### 7.6 异常识别算法与实测指标

- 算法：**分层基线 + 分位数阈值**。按「星期几 × 小时」分组，用前 52 周同槽位历史值的**中位数**作基线；以历史**残差的 0.99 分位数**作阈值上限；
- 为什么不用固定 3σ：建筑逐时电耗近似对数正态、右尾很重，固定 3σ 在完全正常的数据上就有 12.2% 的点超阈值，无法满足误报率 ≤ 10%；
- 实测指标（`docs/eval/anomaly_eval_report.md`）：

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 能耗异常识别 召回率 | ≥ 90% | **98.68%** | ✅ |
| 能耗异常识别 误报率 | ≤ 10% | **3.29%** | ✅ |
| 数据质量缺陷识别 召回率 | ≥ 90% | 97.67% | ✅ |
| 数据质量缺陷识别 误报率 | ≤ 10% | 1.37% | ✅ |

⚠️ 评测采用**注入式仿真**方法，与真实建筑用能异常形态存在差异；算法输出为**初筛结果**，最终处置必须由人工复核。

### 8.1 打不开页面（浏览器显示无法访问）

**现象**：浏览器访问 `http://127.0.0.1:5173` 提示"无法访问此网站"或一直转圈。

**原因**：前端 Vite 开发服务器未启动，或启动失败。

**处理**

```bash
./scripts/start-all.sh status      # 查看 5173 是否在运行
cd frontend && pnpm install        # 首次使用先装依赖
tail -f ../.logs/frontend.log      # 查看启动日志
./scripts/start-all.sh -d          # 重新拉起
```

若 `pnpm run dev` 报端口占用，见 [8.11](#811-端口被占用)。

### 8.2 登录失败

**现象**：点击 **登录** 后提示用户名或密码错误。

**原因与处理**

| 原因 | 处理 |
|---|---|
| 密码输错（注意大小写） | 使用 `admin / admin123`、`operator / operator123`、`viewer / viewer123` |
| 账号被停用 | 提示"账号已停用"，请联系管理员 |
| 后端未启动 | 页面同时会出现网络错误；执行 `curl --max-time 5 http://127.0.0.1:8080/api/system/health` 检查 |
| 数据库无用户表数据 | 执行 `./scripts/mysql.sh status` 确认表已建立；必要时 `./scripts/mysql.sh init` |

💡 系统对"用户名不存在"与"密码错误"返回**同一提示**，这是防止账号枚举的安全设计，不代表账号一定存在。

| 提示／状态 | 含义 | 处理 |

### 8.5 COP 无数据

**现象**：在 **统计分析 → COP 计算** 中选择建筑后，页面显示蓝色提示"该建筑在本区间没有可用的冷冻水计量，无法计算 COP"，所有 COP 指标显示 `--`。

**原因**：BDG2 数据集中多数园区的冷冻水表计计量口径不可用（已按校验规则剔除），**18 个园区中约 5 个能算出 COP**，其余建筑必然返回"无数据"。这是**数据采集现状**，属预期结果。

**处理**

1. 改选有冷水计量的建筑查看完整分析，例如 **`Hog_office_Sydney`**；
2. 在小E 助手中提问时**务必带上建筑编号**；
3. 不要将此现象报告为系统缺陷——对照 [7.3](#73-为什么有些字段是空的) 的缺失率说明即可解释。

### 8.6 查询报"时间跨度过大"

**现象**：查询时提示 `查询时间跨度 N 天超过上限 366 天，请缩小范围`。

**原因**：后端对单次查询的时间跨度有硬性限制（默认 **366 天**），用于防止一次拉取过多数据拖慢系统。

**处理**

- 把 **时间范围** 缩小到 366 天以内，分批查询；
- 需要看全年趋势时，把 **粒度** 切换为 **月**；
- 数据集本身的时间范围是 2016-01-01 ～ 2017-07-01，超出该范围的查询同样会无数据。

### 8.7 小时粒度报错

**现象**：粒度选 **小时** 并选择多栋建筑后点击 **查询**，提示"小时粒度数据量过大，请选择且仅选择 1 栋建筑；多建筑对比请改用日或月粒度"。

**原因**：小时级数据量极大（单栋建筑半年即约 4300 行），多栋建筑一次性返回会导致查询超时。

**处理**

1. 在 **建筑** 下拉中只保留 **1 栋**建筑；或
2. 把 **粒度** 改为 **日** 或 **月**，即可同时对比多栋建筑。

💡 筛选栏在小时粒度下会常驻显示黄色标签"小时粒度仅支持单栋建筑"作为提醒。

### 8.8 AI 助手提示服务不可用

**现象**：小E 助手页顶部显示红色 **AI 服务不可用**；或回答气泡显示"抱歉，AI 服务当前不可用，请稍后重试。"

**原因与处理**

| 原因 | 处理 |
|---|---|
| 后端未启动 | `curl --max-time 5 http://127.0.0.1:8080/api/ai/health` 检查；未通则查看 `.logs/backend.log` |
| 配置为 `http` 模式但外部 AI 服务（默认 8000 端口）未启动 | 启动外部 RAGFlow／FastAPI 服务；或临时改回本地联调模式：设置环境变量 `CARBON_AI_MODE=mock` 后重启后端 |
| 外部 AI 服务响应超时 | 后端配置了连接超时 3 秒、读取超时 60 秒；服务恢复后重试 |

💡 健康接口返回的统一信封中，`data.status` 为 `UP` 表示可用，`data.mode` 为当前模式；小E 页面顶部的状态条与"模式"标签即由该接口驱动。

💡 **`mock` 模式不是"假数据"**：该模式下答案由后端真实调用统计能力与 MCP 工具生成，数字与图表页面一致，可放心用于演示。页面顶部会显示 **模式 mock** 标签与说明。

### 8.9 导入失败或跳过行数多

**现象**：**预览导入** 步骤显示大量"解析失败"或"按规则跳过"，或 **确认导入** 按钮不可点击。

**原因与处理**

| 原因 | 表现 | 处理 |
|---|---|---|
| 必填字段未映射 | 可导入为 0 | 回到 **字段映射**，确认 `建筑编号 *` 与 `监测时间 *` 已映射 |
| 时间格式不统一 | 解析失败明细"原因"为时间解析错误 | 统一为 `yyyy-MM-dd HH:mm` |
| 能耗列混入单位文字 | 解析失败，原始值显示如 `182.4 kWh` | 在源文件中只保留数字 |
| 建筑编号为空 | 解析失败，原因"建筑编号为空" | 补齐编号，或在 **清洗规则** 中设置 **建筑编号前缀** |
| 数据重复 | 按规则跳过数量大，原因含去重 | 属预期；若源数据本无重复，可切换 **不去重** |
| 能耗为负 | 按规则跳过，原因"能耗为负值，已按清洗规则剔除" | 属预期；若误判可关闭 **剔除负值能耗** |
| 单位用错 | 数万行数值偏小 1000 倍 | 在 **清洗规则** 中把 **电量单位** 改为 **MWh（自动 ×1000）** |
| 文件超过 20 万行 | 上传被拒绝 | 拆分为多个文件分批导入 |
| 编码乱码 | 出现乱码字符 | 系统已自动回退 GBK；若仍乱码，请把文件另存为 UTF-8 后重试 |

💡 **预览导入阶段不会写入数据库**，可以放心反复调整规则直到结果满意。

### 8.10 MySQL 连不上

**现象**：后端启动报数据库连接失败；`./scripts/mysql.sh status` 显示"⭕ 未运行"。

**原因**：项目使用**独立 MySQL 实例**（端口 3307，数据目录 `.mysql/`），与外部的 3306 实例无关。该实例未启动、未初始化或异常退出都会导致连接失败。

**处理**

```bash
./scripts/mysql.sh status              # 查看状态
./scripts/mysql.sh start               # 启动；失败时看日志
cat .mysql/log/error.log               # 关键日志

# 首次部署且从未初始化过数据目录
./scripts/mysql.sh init

# 数据目录损坏需要重来时（危险：会清空数据）
./scripts/mysql.sh reset && ./scripts/mysql.sh init
```

补充说明：

- 独立实例的账号为 `root`、**空密码**，连接串为

### 8.11 端口被占用

**现象**：启动时报端口已被占用（`Address already in use`），或脚本提示端口上已有服务。

**处理**

```bash
# 查看三个端口分别被谁占用
lsof -nP -iTCP:3307 -sTCP:LISTEN
lsof -nP -iTCP:8080 -sTCP:LISTEN
lsof -nP -iTCP:5173 -sTCP:LISTEN

# 结束占用进程（把 PID 换成上一条命令查到的进程号）
kill <PID>

# 或一键停掉本项目的全部服务后重新启动
./scripts/start-all.sh stop
./scripts/start-all.sh -d
```

💡 `start-all.sh` 对"端口已被本项目服务占用"的情况会直接跳过并显示 ✅，属于正常行为，不是报错。真正的冲突通常发生在系统上另有服务占用了 8080 或 5173 时。

### 8.12 3D 园区打不开或卡顿

**现象**：3D 园区页面黑屏、楼栋不显示、拖拽卡顿。

**原因与处理**

| 原因 | 处理 |
|---|---|
| 浏览器不支持 WebGL | 改用 Chrome／Edge 最新版 |
| 未开启硬件加速 | 浏览器设置中开启"使用硬件加速模式"后重启浏览器 |
| 所选园区建筑过多 | 页面单次最多绘制 300 栋建筑，属正常上限；可切换园区或缩小窗口 |
| 远程桌面／虚拟机显卡受限 | 换到本地环境演示 |
| 首次进入等待时间较长 | 属正常，页面显示"正在构建 3D 场景…"，稍候即可 |

### 8.13 登录后被弹回登录页

**现象**：刚登录成功，点击任意菜单又回到登录页，并提示"登录已过期，请重新登录"。

**原因**：令牌失效（后端重启、令牌过期），或浏览器禁用了本地存储。

**处理**

1. 重新登录；
2. 若反复出现，检查浏览器是否处于无痕模式或禁用了 `localStorage`；
3. 确认后端进程没有反复重启（查看 `.logs/backend.log`）。

### 附录 E：术语表

| 术语 | 通俗解释 |
|---|---|
| **COP**（机组能效比） | 制冷量 ÷ 输入电功率。通俗说：花 1 度电能搬走多少热量。数值越高越省电，一般 3.0～5.0。本系统中 COP 为**仿真值** |
| **系统能效比** | 制冷量 ÷ 空调系统**总电耗**（含水泵、风机等），比单台机组的 COP 更低、更接近实际 |
| **供回水温差（ΔT）** | 空调冷冻水回水温度减去供水温度。温差过小通常意味着"小温差大流量"，水泵白耗电。本系统中供回水温度为**仿真值** |
| **EUI**（能耗强度） | 单位面积年能耗，kWh/m²·年。用于给不同大小的建筑做横向对比，"每平方米耗不耗能" |
| **能耗评级 A~E** | 在同一**建筑类型内部**按 EUI 分位数分档：A 为最低 20%（最省），E 为最高 20%（最费）。跨类型直接比较没有意义 |
| **负载率** | 设备实际出力 ÷ 额定出力。负载率长期过低会导致机组效率下降（"大马拉小车"） |
| **尖峰平谷** | 电网按时间划分的电价时段。本系统划分：尖峰 10–12／14–17 时；高峰 8–9／13／18–19 时；平段 7／20–22 时；低谷 23–6 时。把可转移负荷挪到低谷时段可省电费 |
| **峰谷差率** | （峰值 − 谷值）÷ 峰值 × 100%。越大说明用电越不均衡、调节空间越大 |
| **基线（baseline）** | 判定"是否异常"的参照值。本系统取"同一星期几、同一小时"的历史中位数，再把当前值与基线比较 |
| **MAD**（绝对中位差） | 一种抗离群点的离散程度度量。相比标准差，它不会被个别极端值带偏，因此本系统用 MAD 计算稳健 z-score |
| **稳健 z-score** | 用 MAD 标准化的偏差得分。通俗说：当前值偏离基线多少个"稳健标准差"，绝对值越大越异常 |
| **分位数阈值** | 取历史残差的 0.99 分位数作为报警线，使误报率可直接由分位数控制（比固定 3σ 更适合重尾数据） |
| **能耗异常** | 数据可信，但用能显著高于同期基线——需要运维排查 |
| **数据质量缺陷** | 表计卡死（连续 24 小时数值不变）或数据缺失造成的无效小时——属于采集问题，**不计入能耗异常** |
| **A 级 / B 级** | A 级＝建筑有独立电表，能耗是实测值，可参与指标评估；B 级＝无独立电表，电耗按面积占比分摊估算，只用于补覆盖度，标记为"未评估" |
| **B 级分摊** | 把"站点剩余电量"（站点总表 − 已有独立电表建筑之和）按建筑面积占比分给没有独立电表的建筑，保证总量守恒 |
| **未评估（-1）** | `anomaly_flag = -1`，表示该记录（B 级建筑）**没有参与**异常识别评估，统计时必须排除 |
| **实测 / 推算 / 仿真 / 标注** | 数据的四种来源：直接测量／公式推导／规则模型生成／算法标注。其中**仿真值不得当作实测值引用** |
| **召回率 / 误报率** | 召回率＝真正异常中被检出的比例；误报率＝被误判为异常的正常的比例。本系统实测 98.68% / 3.29% |
| **MCP 工具** | 供 AI 助手调用的标准数据查询工具，共 7 类：维度查询、概览统计、分解统计、能耗查询、异常扫描、问题诊断、优化建议 |
| **RAG** | 检索增强生成：先从知识库检索依据，再由大模型组织回答，用于让答案可溯源 |
| **mock 模式** | 本地联调模式（`carbon.ai.mode=mock`）。答案由后端真实统计与 MCP 工具计算得出，**不是预设话术**，只是未经过大模型润色 |
| **springdoc / Swagger UI** | 后端接口文档与在线调试界面，访问 `http://127.0.0.1:8080/swagger-ui/index.html` |

### 附录 G：已知限制（风险边界）

1. **空调供回水温度、COP、人员密度为仿真值**——BDG2 无相应实测数据，已在数据字典与界面徽章中标注；
2. **冷冻水／热水表计覆盖率低**——`hvac_kwh` 缺失约 43%、`cop` 缺失率很高（全量口径 95.41%），这是数据源客观限制，非处理缺陷；
3. **B 级建筑电耗为面积分摊估算值**——仅用于补建筑覆盖度，不参与异常识别指标评估；
4. **异常识别采用统计方法**（分层基线 + 分位数阈值）——评测采用注入式仿真，与真实异常形态存在差异；
5. **异常诊断与优化建议为算法初筛**——结论标注"需人工复核"，系统输出不直接作为最终决策依据。
