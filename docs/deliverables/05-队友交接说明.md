### 2.3 参数约束（务必遵守，否则会 400）

| 约束 | 规则 | 错误提示 |
|---|---|---|
| 时间跨度 | ≤ **366 天** | "查询时间跨度 N 天超过上限 366 天，请缩小范围" |
| `granularity=hourly` | 必须且仅指定 **1 个建筑** | "小时粒度查询请指定且仅指定 1 个建筑…" |
| COP 分析 | 必须指定建筑 | "COP 分析必须指定建筑（buildingId）" |

> 建议：LLM 编排时，把用户说的"某栋楼""这栋楼"先解析成 `building_id`
> （格式固定为 `<站点>_<用途>_<名称>`，如 `Hog_office_Sydney`），可用工具 1 获取候选列表。

### 2.4 数据口径（回答时必须遵守，涉及合规）

数据集中每个字段都有**来源标注**，你的回答必须区分，不得把仿真值说成实测值：

| 来源 | 字段 |
|---|---|
| **实测** | `electricity_kwh`、`hvac_kwh`、`water_m3`、`air_temperature_c`、`area_m2`、`building_type_cn` |
| **推算** | `humidity_pct`（露点→Magnus 公式）、`carbon_kg`、`hvac_electricity_kwh` |
| **仿真** | `chw_supply_temp_c`、`chw_return_temp_c`、`cop`、`occupancy_density` |
| **标注** | `anomaly_flag`、`equipment_status`、`severity`、`data_quality_flag` |

**重要区分**（申报表第 17 条要求）：
- **能耗异常**（`anomaly_flag=1`）是真实用能异常，用于召回率/误报率评估
- **数据质量缺陷**（`data_quality_flag=1`）是表计卡死/数据缺失等采集侧问题，**不是能耗异常**

另外：`anomaly_flag = -1` 表示**未评估**（B 级站点分摊建筑），统计时须排除。

### 2.5 响应封装建议

后端返回统一信封：

```json
{ "code": 200, "message": "操作成功", "data": { }, "success": true, "timestamp": 1791899556589 }
```

建议你的 MCP Server 包装成契约中定义的 MCP 信封：

```json
{
  "ok": true,
  "tool": "query_energy",
  "data": { },
  "meta": { "row_count": 168, "elapsed_ms": 42,
            "data_source": "实测|推算|仿真|混合",
            "generated_at": "2026-01-01T00:00:00+08:00" },
  "error": null
}
```

**注意**：`data` 中的能耗字段**允许为 null**（园区无该表计时合法缺失）。
`cop` 缺失率 **95.41%**（18 个园区中仅 5 个有可用冷冻水表计），
所以 COP 类问题经常返回"无数据"，这是**数据源客观限制**，请在回答中说明，不要报错。

### 10.3 我已有的设计（你实现时请对齐）

- **一次批量规划**：不是逐列调用，而是把全部列的画像一次性给模型，减少 token 与延迟；
- **最小化数据外泄**：只发列名 + 类型 + 每列最多 3 个脱敏样例（截断 40 字符），不发原始数据文件；
- **三种容错**（实测大模型常见毛病）：
  ① 用 markdown 代码块包裹 JSON → 剥离围栏；
  ② JSON 前后带解释文字 → 截取首 `{` 到末 `}`；
  ③ 给出不存在的列名或非法 targetField → 丢弃该条不报错；
- **冲突消解**：同一目标字段被多列命中时保留置信度最高者；
- **必填自动补齐**：即使模型漏给 `building_id`/`timestamp`，也用规则引擎结果补齐，避免整批无法导入；
- **降级**：模型超时/不可用/返回不可解析时，自动回退规则引擎，演示不中断。
