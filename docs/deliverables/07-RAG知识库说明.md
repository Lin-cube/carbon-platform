# RAG 知识库模块说明

> 面向对象：项目负责人 / 答辩讲解人 / 后续维护者
> 目的：说清「RAG 是什么、本项目为什么这么做、怎么用、效果如何、边界在哪」

---

## 一、先用一句话说清 RAG 是什么

**RAG（Retrieval-Augmented Generation，检索增强生成）＝ 先查资料，再回答。**

大模型本身有你不知道的知识，但它：
1. 不知道你项目的私有资料（手册、规范、内部文档）；
2. 会"一本正经地胡说"（幻觉），且无法追溯出处；
3. 知识有截止时间。

RAG 的思路是：**不指望模型记住，而是每次回答前先把相关资料检索出来，塞进模型的上下文里让它照着答**。好处是答案有出处、可更新（改资料即可）、可溯源。

```
不用 RAG：用户提问 → 大模型凭记忆回答 → 可能编造，无出处
用 RAG：  用户提问 → 检索知识库找到相关片段 → 大模型只依据片段回答 → 标注出处
```

**一个关键认知**（也是本项目踩到的第一个坑）：

> RAG 的效果上限由**知识库内容**决定，不由检索算法或框架决定。
> 知识库里没有的内容，换 RAGFlow、Dify、自建都一样答不出来。

## 二、本项目的实际情况：先解决了语料问题

项目初期导入了一份 `sikong_knowledge_base.txt`（2.9 MB，8,805 条问答）。实测诊断后发现：

| 领域关键词 | 命中条数 | 说明 |
|---|---|---|
| 能耗监测 / 分项计量 | **0** | 完全没有 |
| 碳排放 / 碳达峰 | **0** | 完全没有 |
| 运维 | **0** | 169 条"检修/报警"实际来自消防、无障碍规范 |
| 运行调节 / 设定值 / 群控 | 4 | 几乎没有 |
| COP / 性能系数 | 8 | 极少 |
| 小温差 / 大流量 | **0 / 0** | 完全没有 |

**结论：这份语料是「建筑设计规范问答集」**（GB50352 民用建筑设计、GB50368 住宅、JGJ66 博物馆、JGJ38 图书馆…），**不是「建筑能源运维知识库」**。

用它回答"小温差大流量有什么危害"，BM25 检索出来的 TOP1 是"学校与铁路的距离要求"——**不是算法不行，是语料里没有**。

因此本项目把 RAG 拆成两件事：**① 补语料 ② 建检索**。多数人只做②，这是效果差的根本原因。

## 三、本项目的 RAG 架构

```
                        ┌─────────────────────────────────────┐
   用户提问 ──────────▶ │  后端 HybridAiServiceClient（路由）  │
                        └──────────────┬──────────────────────┘
                                       │
                    ┌──────────────────┴──────────────────┐
                    │                                     │
              【知识类问题】                          【数据类问题】
          "小温差大流量有什么危害"                "Eagle 园区用电量多少"
                    │                                     │
                    ▼                                     ▼
        ┌───────────────────────┐            ┌────────────────────────┐
        │  RAG 服务（FastAPI）   │            │  本地统计引擎           │
        │  端口 8000            │            │  (MockAiServiceClient) │
        │                       │            │                        │
        │  混合检索：            │            │  直接查 MySQL：         │
        │   · BM25（jieba 分词） │            │   · 真实统计 SQL        │
        │   · 字符 n-gram 向量   │            │   · 30 个 REST 接口     │
        │   · 类别加权           │            │                        │
        │   · 领域术语加分       │            │  → 返回精确数值         │
        │                       │            └────────────────────────┘
        │  → 返回原文 + 出处     │
        └───────────────────────┘
```

### 3.1 为什么必须做「混合路由」

这是本项目实测踩出来的坑：把后端配成 `carbon.ai.mode=http`（全部走 RAG）后，
"统计 Eagle 园区用电量"这类问题也被送去知识库检索，返回一堆无关的规范条文——
**数据类问题的准确率直接崩掉**。

因为两个引擎的能力边界完全不同：

| 引擎 | 擅长 | 不擅长 |
|---|---|---|
| 本地统计 | 需要查数据库的问题（用电量、异常率、COP 数值） | 专业知识、规范条文 |
| RAG 知识库 | 运维知识、处置方法、规范依据（可溯源） | 具体数值统计（它没有数据库权限） |

所以默认配置 `carbon.ai.mode=hybrid` 做按问题类型路由。路由规则有**优先级**：

1. **含具体建筑编号**（如 `Hog_office_Sydney`）→ 本地统计
   *踩坑记录："Hog_office_Sydney 这栋楼为什么能耗偏高"含"为什么"，曾被误判为知识类路由到 RAG，但知识库无法回答具体建筑的诊断。*
2. **命中数据类强特征词**（"总用电""占比""统计""异常率""缺失率"…）→ 本地统计
3. **命中知识类特征词**（"什么是""危害""标准步骤""规范""怎么处理"…）→ RAG
4. 都不命中 → 本地统计（保守策略，保证数据类问题不退化）

### 3.2 语料的四个来源

| 来源 | 条数 | 占比 | 说明 |
|---|---|---|---|
| 设计规范 QA（司空知识库） | 8,805 | 98.7% | 外部导入，标注为「设计规范」类 |
| 项目数据字典 | 61 | 0.7% | 从 `docs/data_dictionary.md` 自动提取字段说明 |
| 项目文档 | 8 | 0.1% | 从评测报告自动提取结论段落 |
| **运维知识（自建）** | **47** | **0.5%** | **手工撰写，见下表分主题** |

**运维知识按主题拆成 6 个文件**（便于维护与扩充）：

| 文件 | 条数 | 覆盖内容 |
|---|---|---|
| `hvac_operations.json` | 9 | 核心概念：供水温度、小温差大流量、COP 下降、夜间基载、异常排查、能耗评级、数据口径 |
| `chiller_cooling.json` | 8 | 冷机与冷却水：冷凝温度影响、冷却塔故障、水质管理、离心机喘振、加减机策略、保养、冷媒泄漏、冷却水温优化 |
| `water_air_system.json` | 9 | 水系统与末端：相似定律、定/变流量、水力失衡、定压排气、水泵故障、AHU、VAV、新风、除湿再热 |
| `heating_operation.json` | 9 | 热源与运行管理：锅炉效率、垂直失调、气候补偿、热源选型、四个抓手、分项计量、季节切换、峰谷电价、改造顺序 |
| `diagnosis_dataquality.json` | 6 | 故障诊断：数据/设备异常区分、传感器漂移、流量计故障、不冷排查树、能耗升高排查、假故障 |
| `comfort_metrics.json` | 6 | 舒适与指标：PMV/PPD、湿度影响、EUI 口径、COP/EER/SCOP、季节性、碳核算 |

**运维知识虽然只有 9 条，却是回答核心问题的关键**。每一条都带来源标注：

| 来源类型 | 含义 | 可信度 |
|---|---|---|
| `principle` | 暖通空调/传热学基本原理推导，物理上成立 | 最高 |
| `practice` | 行业通用运维实践做法（经验共识） | 高 |
| `project` | 本项目自身设计与算法说明 | 高 |
| `standard_ref` | 涉及标准但未获取原文，仅指出方向 | **需核实** |

**不编造规范条文**：涉及具体标准数值时明确标注"需核实"，宁可少答也不答错。

### 3.3 检索算法：为什么用「BM25 + 字符 n-gram」而不是神经向量

| 方案 | 优势 | 本项目的取舍 |
|---|---|---|
| BM25（关键词） | 精确术语强（"COP"、"GB50189"、"小温差"） | ✅ 采用 |
| 神经向量模型（如 BGE） | 语义泛化强 | ❌ 未采用：需下载约 400MB 权重，本机 16GB 内存需同时跑 MySQL + Spring Boot + Node + RAG |
| **字符 n-gram TF-IDF** | 中文无需分词即可捕捉共享语素（"夜间基载"↔"待机能耗"） | ✅ 采用，零模型下载 |

**两路分数各自 min-max 归一化后按 0.55 / 0.45 加权融合**，再加两项修正：

- **类别加权**：语料严重不平衡（规范占 99%，运维占 0.1%），若不加权，运维内容会被规范文本淹没。运维知识 ×3.2、数据字典 ×1.8、项目文档 ×1.6、设计规范 ×1.0。
- **领域术语加分**：问句中的领域术语（"小温差""基载""COP"…）若出现在正文中，额外加分。

> 检索接口预留了 embedding 后端插槽，后续若内存允许可平滑替换为神经向量模型。

## 四、怎么用（三条路径）

### 路径 1：通过系统界面（最终用户）

1. 打开 http://127.0.0.1:5173 ，用 `admin / admin123` 登录
2. 进入「小E 助手」页面
3. 直接提问，例如：
   - 「什么是小温差大流量，有什么危害」→ 走知识库，返回原文 + 出处
   - 「统计 Eagle 园区 2016 年用电量」→ 走本地统计，返回精确数值

回答下方会显示**引用出处**（来源文件、分类、可信度），可点击核对原文。

### 路径 2：直接调接口

```bash
# RAG 服务健康检查（含知识库规模）
curl http://127.0.0.1:8000/health

# 知识问答
curl -X POST http://127.0.0.1:8000/ai/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"冷水机组 COP 下降的常见原因有哪些","topK":3}'

# 只做检索（不生成），用于调试
curl -X POST http://127.0.0.1:8000/mcp/call \
  -H 'Content-Type: application/json' \
  -d '{"tool":"search_knowledge","arguments":{"query":"夜间基载","topK":5}}'
```

### 路径 3：命令行直接检索（调试语料用）

```bash
cd carbon-platform
.venv/bin/python rag-service/src/retriever.py "小温差大流量有什么危害"
```

## 五、怎么维护（改语料 / 加语料）

### 5.1 新增运维知识

编辑 `rag-service/corpus/hvac_operations.json`，按现有格式追加一条：

```json
{
  "id": "HVAC-010",
  "title": "条目标题（会参与检索，权重较高）",
  "tags": ["关键词1", "关键词2"],
  "source_type": "principle",
  "confidence": "high",
  "content": "正文内容。可用 \n 分段，用【】分小节。",
  "note": "可选：需要提示用户的注意事项"
}
```

然后**重建索引**：

```bash
.venv/bin/python rag-service/src/build_index.py
```

### 5.2 换掉/新增外部语料

- 修改 `rag-service/src/build_index.py` 中的 `SIKONG` 路径，或新增一个 `load_xxx_corpus()` 函数
- 支持格式：QA 对文本（`【问题】…【答案】…`）、JSON（见 `hvac_operations.json`）、Markdown 表格

### 5.3 重建后必须重启 RAG 服务

索引是启动时加载到内存的，改完要重启：

```bash
./scripts/start-all.sh stop && ./scripts/start-all.sh -d
```

| 夜间基载偏高说明什么问题 | ✅ HVAC-005 |
| 能耗评级 A 到 E 是怎么划分的 | ✅ HVAC-006 |

**6/6 = 100%**

### 6.1.1 三组评测结果（必须一起看，否则会高估）

| 测试集 | 题量 | 措辞特点 | TOP1 | TOP3 | 可信度 |
|---|---|---|---|---|---|
| **A 撰写测试集** | 24 | 与我写语料时用词一致 | 100% | — | ❌ **不可引用**（同一人写语料和题目） |
| **B 留出集（已用于调优）** | 36 | 口语化，**曾用于补同义词** | 97% | 100% | ⚠️ 调优后值，偏乐观 |
| **C 留出集（真留出）** | 37 | 全新口语措辞，**写完即测、未调优** | **57%** | **78%** | ✅ **这才是真实泛化能力** |

**结论：54%~78% 是当前检索方案在「用户口语提问」下的真实水平**，不是 100%。
答辩时若被问准确率，应说清楚是哪组口径，否则属于误导。

C 组未命中的 8 题及原因（这批题在写语料时完全没有考虑）：

| 用户问法 | 期望条目 | 为什么没中 |
|---|---|---|
| 塔上水花溅得到处都是 | 冷却塔飘水 | 「溅得到处都是」未在标签中 |
| 开机时机器一阵一阵地吼 | 离心机喘振 | 「一阵一阵地吼」未在标签中 |
| 泵吸不上水 | 水泵气蚀/流量不足 | 标签写的是「泵不抽水」 |
| 暖气片上面烫下面温 | 供暖垂直失调 | 「暖气片」未在标签中 |
| 电费账单看不出明细 | 分项计量 | 「电费账单」未在标签中 |
| 春秋换季空调怎么处理 | 季节切换 | 「换季」有标签，但被「分项计量」抢走 |
| 办公室一直不凉快 | 不冷排查树 | 短查询被设计规范里的「办公室」名词解释抢走 |
| 房间里干得难受 | 湿度影响 | 被「空调不冷」抢走 |

**两类失败原因**：
1. **口语词汇无法穷举** —— 关键词检索的固有局限。想真正解决需要语义向量模型（见 §八）；
2. **短查询被规范文本抢位** —— 语料 187:1 不平衡。曾尝试「运维知识晋升规则」，
   实测无收益且会把规范类问题误判为运维类，已回退。

### 6.2 24 题问答测试集（申报表验收指标 2：≥85%）

| 类别 | 题量 | 判据 | 结果 |
|---|---|---|---|
| 数据/统计类 | 22 | 答案要点命中率 ≥50% | **22/22 = 100%** |
| 知识类 | 6 | RAG 检索命中期望条目 | **6/6 = 100%** |
| **综合可判定准确率** | **28** | — | **28/28 = 100%** ✅ |
| MCP 工具路由正确率 | 24 | 是否调用期望工具 | 22/24 = 91.7% |

> **判分口径必须说明**：知识类题目以「检索是否命中期望知识条目」为客观判据。
> 系统当前已接入 **DeepSeek**（`deepseek-chat`）做答案生成，回答会引用检索内容并标注出处；
> 但"生成答案质量"目前**未做自动判分**，需人工抽检。
> 若后续改为评价生成质量，需重新评测，不能沿用本表的 100%。

### 6.3 性能

| 项 | 实测 |
|---|---|
| 知识问答端到端（纯检索模式） | **23 ~ 27 ms** |
| 知识问答端到端（DeepSeek 生成模式） | **2.0 ~ 3.2 s**（P95 2.4~3.1s） |
| 检索耗时（8893 条语料内） | < 10 ms |
| 索引构建耗时 | 4.5 s |
| 索引内存占用 | 约 200 MB |
| DeepSeek 单次生成 | 约 1.8~2.4 s（受输出长度影响，见下） |

**关于延迟的实测发现**：大模型延迟与**输出长度近似线性**——实测 35 token ≈ 1.8s、
500 token ≈ 2.1s、644 token ≈ 5.2s。因此已做两项优化：

1. `max_tokens` 限制为 500（环境变量 `CARBON_LLM_MAX_TOKENS` 可调）；
2. 系统提示词要求"总长度控制在 500 字以内，不复述片段原文、不重复引用"。

优化后稳定在 2.0~3.2s。**这是外部 API 往返的物理下限，继续压缩只能牺牲答案完整性。**
因此压测报告把「AI 生成类接口」与「核心接口」分开统计：验收指标 1（核心页面 P95 ≤ 2s）
针对的是本地系统性能，不包含外部大模型延迟。

## 七、为什么不用 RAGFlow（决策记录）

申报表原文提到 RAGFlow，本项目最终采用自建轻量方案，理由如下：

| 维度 | RAGFlow | 本项目自建 |
|---|---|---|
| 前置成本 | 需 Docker Desktop（约 1GB）+ 拉取 9 个容器镜像 | 零额外安装 |
| 内存占用 | ≥4 GB（Elasticsearch/MySQL/Redis/MinIO…） | 约 200 MB |
| 本机资源 | 16GB 需同时跑 MySQL + Spring Boot + Node，会紧张 | 有余量 |
| **文档解析能力** | **强项** —— 但本项目语料**已是结构化 QA 对**，用不上 | 不需要 |
| 检索质量 | 内置混合检索，更成熟 | 自研，可调、可解释 |
| 答辩表述 | "基于 RAGFlow 构建" | "自研混合检索链路，BM25 + 字符 n-gram + 类别加权" |

**核心判断**：RAGFlow 最大的价值是解析复杂 PDF/Word 并智能分块。
本项目语料已经是 8,805 条现成问答对，这项能力完全用不上；
花装 Docker 与 4GB 内存去换一个用不上的能力不划算。

**如果后续需要**（例如拿到了大量 PDF 版规范原文需要解析），可以再部署 RAGFlow 作为
额外的知识源，本项目的检索层已预留多语料源接口，两者可以共存。

> 不能作为泛化能力证据。建议补充一批未参与调优的运维问题作为留出集再报分。
