## 一、一句话结论

> 导入后，新建筑会出现在**建筑列表、3D 园区、能耗查询、监控看板、统计分析**五个位置；
> **不会**出现在异常诊断里（因为新数据没有历史基线，无法判定异常）。

> **看板、日/月趋势、园区分解全都看不到**。

### 第 11 项为什么永远看不到

异常诊断读的是 `fact_anomaly_event`（异常事件表），而导入不写这张表。
原因是**异常检测需要 52 周同槽位历史基线**：

- 新导入的建筑只有几小时~几天的数据，没有历史基线可比；
- 强行判异常会让"正常波动"被标成异常，污染召回率/误报率这两个验收指标。

所以导入的数据 `anomaly_flag = -1`（未评估），这是**设计选择，不是缺陷**。
如果希望新数据参与异常检测，需要：

1. 导入至少 **52 周**的历史数据；
2. 重新运行异常标注脚本：
   ```bash
   .venv/bin/python data-pipeline/scripts/02_build_unified_dataset.py
   ```

## 四、建筑维表与园区维表是怎么构建的

### 4.1 三张维表的分工

| 表 | 作用 | 谁在用 |
|---|---|---|
| `dim_building` | 建筑档案：编号、园区、类型、面积、评级、EUI | 建筑列表、3D 渲染、类型分解、评级分布 |
| `dim_site` | 园区档案：编号、名称、建筑数 | 3D 页面的园区下拉、园区分解 |
| `fact_energy_hourly` | 逐小时能耗明细 | 能耗查询、图表数据 |

### 4.2 导入时自动登记（本次修复）

导入时如果遇到**库中没有的建筑**，会自动建档：

| 属性 | 来源 | 缺失时 |
|---|---|---|
| `building_id` | CSV 的「建筑编号」 | 必填，缺失则整行跳过 |
| `site_id` | CSV 的「园区编号」 | 填 `IMPORTED` 并建对应园区 |
| `building_type_cn` | CSV 的「建筑类型」 | 填「未知」 |
| `area_m2` | CSV 的「建筑面积」 | 留空 → 无法算 EUI 与评级 |
| `data_grade` | 固定为 `A` | 导入的是实测数据，按 A 级处理 |
| `meter_source` | 固定为「导入登记」 | 便于追溯来源 |
| `energy_grade` / `eui_kwh_m2_year` | 导入后自动计算 | 数据不足 30 天则留空 |

> **已存在的建筑不会被覆盖**。导入只会：
> - 补 `site_id`（若原为空）；
> - 补 `building_type_cn`（若原为「未知」）；
> - 补 `area_m2`（若原为空）。
>
> 人工维护过的值绝不会被导入动作冲掉。

### 4.3 能耗评级怎么算的

采用**同类型内分位数法**（与数据管道一致）：

```
EUI = 年化电量 ÷ 建筑面积          （单位 kWh/m²·年）
     = 实际电量 ÷ 面积 × (8760 ÷ 实际小时数)

在同建筑类型的其他建筑中：
  EUI ≤ 20% 分位 → A
  EUI ≤ 40% 分位 → B
  EUI ≤ 60% 分位 → C
  EUI ≤ 80% 分位 → D
  其余          → E
```

**为什么用分位数而不是绝对阈值**：教学楼与数据中心的能耗强度天然不同，
绝对阈值（如「EUI > 200 即不合格」）在不同业态下会严重失真。

**三道安全门槛**（防止给出误导性评级）：

| 门槛 | 原因 |
|---|---|
| 无建筑面积 → 不评级 | EUI 无法计算 |
| 同类型样本 < 5 栋 → 不评级 | 分位数无统计意义 |
| **数据覆盖 < 30 天 → 不评级** | 实测教训：用 3 小时数据年化得到 EUI=432，直接判 E 级，属误导 |

## 五、新数据能干什么（实际用途）

导入的数据不是"存着好看"，它在系统里有四类实际作用：

### 5.1 参与统计口径

导入的数据会**立刻计入**所在时间段的所有统计：KPI 总电量、趋势图、
园区分解、建筑类型结构、峰谷分时占比。也就是说导入后看板的数字会变。

### 5.2 支撑对比分析

同一栋楼导入多个时间段的数据后，可以做：
- 同比 / 环比（今年 7 月 vs 去年 7 月）
- 改造前后对比（改造前 3 个月 vs 改造后 3 个月）
- 跨建筑横向对比（同类型建筑 EUI 排名）

### 5.3 触发能耗评级

导入足够数据（≥30 天）+ 提供建筑面积后，建筑会获得 A–E 评级，
并进入 3D 园区的着色逻辑与看板的评级分布图。

### 5.4 进入 AI 问答的取数范围

"Eagle 园区 2016 年用电量多少"这类问题，AI 会调后端统计接口取数。
导入的数据会自动纳入统计范围，因此 AI 回答里的数字会包含它。

**唯一不参与的是异常检测**（见 §三第 11 项）。

## 十、审计留痕怎么读（每批数据到底入库了吗）

「历史导入批次」列表里会同时出现 `预览通过` 和 `成功 / 部分成功`，**含义完全不同**：

| 状态 | 是否写入数据库 | 说明 |
|---|---|---|
| **预览通过** | ❌ **没有** | 只做了演练：解析、映射、清洗、统计都算了，但**不写库**。用于落库前检查 |
| **成功** | ✅ 已写入 | 全部行处理完成（跳过的行除外） |
| **部分成功** | ✅ 已写入 | 有失败行，但成功的行已经入库 |

> 2026-10 版界面已增加独立的 **「是否入库」列**（`已入库` / `未入库（预览）`），
> 数据库 `data_import_log.dry_run` 字段明确记录，不再依赖状态文字猜测。

### 数据去了哪里

已入库的数据落在两处：

| 位置 | 内容 |
|---|---|
| `fact_energy_hourly` | 逐小时明细（能耗查询、图表取数） |
| `dim_building` / `dim_site` | 建筑与园区档案（下拉框、3D 渲染、分组统计） |

同时会**增量刷新 4 张预聚合表**（`agg_building_daily` 等），所以看板、日/月趋势、园区分解
都能立刻看到新数据。

### 重复导入会怎样

按「建筑 + 时刻」**覆盖**：同一栋楼同一小时重复导入不会产生重复行，只会替换。
因此反复测试同一份文件，事实表行数不会累加。

### 怎么核对某个批次的行是否还在库里

数据表没有记录 `batch_no`，无法直接按批次反查。可用以下方式间接核对：

```sql
-- 1. 看某建筑的数据是否存在
SELECT COUNT(*), MIN(ts), MAX(ts) FROM fact_energy_hourly WHERE building_id = '你的建筑编号';

-- 2. 看建筑是否已登记
SELECT * FROM dim_building WHERE building_id = '你的建筑编号';

-- 3. 看该批次的字段映射与清洗规则
SELECT field_mapping, clean_rules, status, dry_run FROM data_import_log WHERE batch_no = '批次号';
```

### 真正的批次追溯（2026-10 新增）

早期版本的事实表没有批次标记，导致"批次可追溯"只是名义上的——只能查到"某次导入做了什么"，
无法回答"这行数据来自哪次导入"，也无法撤销某一批。

现已补齐：

| 能力 | 实现 |
|---|---|
| 每行数据带批次号 | `fact_energy_hourly.import_batch_no`（`NULL` = 初始数据集） |
| 按批次查行数 | 审计列表直接显示「库中行数」列 |
| 按批次看数据 | `GET /api/import/logs/{id}/rows` |
| 按批次追溯范围 | `GET /api/import/logs/{id}/trace`（行数、建筑数、时间范围） |
| **按批次回滚** | `POST /api/import/logs/{id}/rollback`（删数据 + 刷新预聚合 + 状态改「已回滚」） |
