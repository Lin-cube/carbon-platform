# 服务器配置需求评估

> 本文基于**本机实测资源占用**推算服务器配置，不是拍脑袋估算。
> 测量时间：项目完成态（599 万行数据、30 个接口、RAG 服务全部运行）。

---

## 一、结论先说

| 配置 | 内存 | CPU | 结论 |
|---|---|---|---|
| 2 核 2G | 够（实测约 900MB） | 够（最慢接口 292ms×2.5≈730ms） | ✅ 可用，需按 §4 调优 |
| 2 核 4G | 充裕 | 够 | ✅ **推荐**（48 元/月档位即此配置） |
| 4 核 4G | 充裕 | 宽裕 | ✅ 更好，可支撑更多并发 |
| 4 核 8G | 很充裕 | 宽裕 | ✅ 舒适 |

**一句话**：内存不是瓶颈（实测只需约 900MB），CPU 经优化后**在 2 核上也能满足 P95 ≤ 2 秒**。

> **优化说明**：初评时最慢核心接口为 689ms（按 2.5 倍折算约 1.6s，接近 2 秒线，存在风险）。
> 后续定位到「带园区过滤」的时段统计会回退到 600 万行事实表，
> 通过新增 `agg_site_hourly`（23.7 万行）解决，最慢接口降至 **292ms**，
> 2 核折算约 **730ms**，留出充足余量。

## 二、内存实测数据

### 2.1 各组件真实占用（本机 macOS ARM 测得）

| 组件 | 默认配置 RSS | 调优后 RSS | 说明 |
|---|---|---|---|
| MySQL 8.4 | 169 MB | ~350 MB | 服务器上会把 buffer pool 调大，反而略增 |
| Spring Boot (JDK 21) | **597 MB** | **251 MB** | 见 §2.2，调 JVM 参数后大幅下降 |
| Python RAG (FastAPI) | 65 MB | ~80 MB | 加载 8,883 条索引 |
| Node / Vite（开发服务器） | 142 MB | **0**（生产用 nginx ~15MB） | 生产环境跑 `dist` 静态文件，不需要 Node |
| **合计** | **973 MB** | **≈ 696 MB** | |

### 2.2 关键发现：JVM 内存可以压缩 58%

用 `jcmd GC.run` 强制 GC 后观察真实存活对象：

```
garbage-first heap   total 131072K, used 32652K     ← 存活对象仅 32 MB
Metaspace            used 69356K                     ← 元空间 69 MB
```

**这说明**：597MB RSS 里绝大部分是**未回收的浮动垃圾**。
JDK 21 默认最大堆是物理内存的 1/4，本机 16GB → 4GB 堆，
JVM 没有压力就不急着 GC，RSS 自然虚高。

**实测把 JVM 参数改为 `-Xmx384m -Xss512k -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC` 后**：

| 指标 | 默认 | 受限配置 |
|---|---|---|
| RSS | 597 MB | **251 MB** |
| 功能可用性 | 正常 | 正常（30 个接口全 200） |
| 时段汇总查询 | 659 ms | 864 ms（慢 31%，仍 < 2s） |

> 也就是说：**Spring Boot 后端在 251MB 内存下能完整正常工作**。

### 2.3 服务器内存预算（2G 机器）

| 项 | 占用 |
|---|---|
| Linux 系统基础 | ~200 MB |
| MySQL（buffer pool 256M） | ~350 MB |
| 后端 JVM（-Xmx384m） | ~251 MB |
| RAG 服务 | ~80 MB |
| Nginx（静态前端） | ~15 MB |
| **合计** | **≈ 896 MB** |
| **剩余给页缓存** | **≈ 1.1 GB** |

**结论：2G 内存装得下，剩下 1.1GB 还能给文件系统做缓存**。不会 OOM。

## 三、CPU 才是真正的瓶颈

### 3.1 实测查询耗时（M4，10 核）

| 接口 | 耗时 | 性质 |
|---|---|---|
| `/api/system/overview`（冷，真实 COUNT） | 441 ms | 扫 600 万行 |
| `/api/system/overview`（命中缓存） | 8 ms | — |
| `/api/analytics/period-summary` 按月 | 659~864 ms | 聚合 |
| `/api/energy/breakdown` 按类型 | 243 ms | 聚合 |
| `/api/analytics/anomaly` | 259 ms | 聚合 |
| `/api/energy/query` 日粒度 | 93 ms | 明细 |
| 其余接口 | < 30 ms | — |

### 3.2 折算到 2 核云服务器

苹果 M4 单核性能约为常见云服务器 vCPU（Xeon Platinum 2.5GHz 级别）的 **2.5~3 倍**。
按 2.5 倍保守折算：

| 接口 | 本机 | 2 核云服务器（估算） |
|---|---|---|
| overview（冷） | 441 ms | **1.1 s** |
| period-summary | 659 ms | **1.6 s** |
| period-summary（受限 JVM） | 864 ms | **2.2 s** ⚠️ 超标 |
| breakdown | 243 ms | 0.6 s |
| 其余 | < 260 ms | < 0.7 s |

**风险点已消除**：优化后最慢接口为 292ms，2 核折算约 730ms。
详见 §3.4 的优化记录。

### 3.3 缓解措施（已实施 + 建议）

| 措施 | 状态 | 效果 |
|---|---|---|
| 4 张预聚合表 | ✅ 已做 | 最慢接口从 4.6s 降到 0.15s |
| overview 进程内缓存 | ✅ 已做 | 1824ms → 8ms |
| 前端静态托管（不跑 Vite） | 📋 部署时做 | 省 142MB 内存 + 一个 Node 进程 |
| 预聚合表覆盖 period-summary | 📋 可选优化 | 可再降 30~50% |
| 降低数据量（如只导入 1 年） | 📋 应急方案 | 行数减半，查询线性变快 |

### 3.4 关键优化：消除「园区过滤回退事实表」

初评时发现一个隐藏瓶颈：

| 请求 | 优化前 |
|---|---|
| `period-summary?periodType=month`（无过滤） | 146 ms |
| `period-summary?periodType=month&siteId=Eagle` | **685 ms** |

同样查询只多了一个园区条件，耗时涨 4.7 倍。根因是 `agg_time_hourly`
（跨建筑小时汇总）**没有 `site_id` 列**，一旦带园区过滤就回退到 600 万行事实表。

**解决方案**：新增 `agg_site_hourly`（园区 × 日期 × 小时，236,523 行），
并改造 SQL 为三级数据源选择：

| 查询条件 | 使用表 | 行数 | 实测 |
|---|---|---|---|
| 无过滤 | `agg_time_hourly` | 13,140 | 3 ms |
| 仅园区过滤 | `agg_site_hourly` | 236,523 | 4 ms |
| 按建筑过滤 | `fact_energy_hourly` | 5,991,840 | ~500 ms |

**效果**：

| 请求 | 优化前 | 优化后 |
|---|---|---|
| month + siteId | 685 ms | **53 ms** |
| day + siteId | — | 68 ms |
| 最慢核心接口 | 689 ms | **292 ms** |

**数据一致性已验证**：全量总电量 614,125,848 kWh、峰值时段 14:00、
园区 Eagle 总电量 72,336,056 kWh —— 与优化前完全一致。

### 3.5 带宽需求

前端构建产物 2.9 MB（未压缩），首屏 gzip 后约 **759 KB**：

| 资源 | gzip 后 |
|---|---|
| Element Plus | 375 KB |
| ECharts | 229 KB |
| Three.js（3D 园区单独分包，只在进 3D 页时加载） | 119 KB |
| 应用代码 | 36 KB |

按标称 **15 M 出站带宽**折算：

| 项 | 值 |
|---|---|
| 理论下载速度 | 1.88 MB/s |
| 首屏首次加载 | **0.4 s**（之后走浏览器缓存） |
| 单用户峰值占用 | ~0.5 MB/s |
| 可撑并发（同时首屏加载） | 约 5 人 |

**结论：15M 带宽对答辩演示完全够用**。若后续要给几十人同时用，才需要升带宽。

## 四、2 核 2G 的部署调优清单

如果确定买 2C2G，按以下配置部署才稳。

### 4.1 MySQL 配置（`my.cnf`）

```ini
[mysqld]
# 内存：控制在 350MB 以内
innodb_buffer_pool_size = 256M
innodb_log_buffer_size  = 16M
key_buffer_size         = 16M
max_connections         = 50
tmp_table_size          = 32M
max_heap_table_size     = 32M

# 磁盘：关闭 binlog 可省 4.2GB（本项目不需要主从复制）
skip-log-bin
# 若必须保留 binlog，限制保留天数
# binlog_expire_logs_seconds = 259200

# 性能
innodb_flush_log_at_trx_commit = 2
innodb_flush_method = O_DIRECT
```

> **实测磁盘构成**（本机）：表数据 2.5GB + binlog 4.2GB + undo 640MB = 8.1GB。
> 迁移时用 `mysqldump` 只导出表，**不要整目录拷贝**，可省掉大部分空间。

### 4.2 JVM 参数

```bash
java -Xmx384m -Xss512k -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC \
     -jar carbon-platform-backend.jar
```

- `-Xmx384m`：实测存活对象仅 32MB，384MB 有 12 倍余量
- `-XX:+UseSerialGC`：小堆用串行 GC 比 G1 更省内存（省下 G1 的 region 管理开销）
- 实测该配置 RSS 251MB，功能完全正常

### 4.3 前端用 Nginx 静态托管（不要跑 `pnpm dev`）

```bash
# 1. 本机构建
cd frontend && pnpm run build        # 产出 dist/（2.9MB）

# 2. 上传 dist 到服务器
scp -r dist/* user@server:/var/www/carbon/

# 3. nginx 配置
server {
    listen 80;
    server_name your-domain.com;
    root /var/www/carbon;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;   # Vue Router history 模式必需
    }
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_read_timeout 120s;            # AI 问答需要较长超时
    }
}
```

> 省下 Node 的 142MB 内存和一个进程，这是 2G 机器上**必须做**的优化。

### 4.4 Python RAG 服务

```bash
cd rag-service/src
../../.venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8000 --workers 1
```

**必须 `--workers 1`**：索引占内存，多 worker 会复制多份。
单 worker 足够（检索耗时 < 10ms）。

### 4.5 磁盘需求

| 项 | 大小 |
|---|---|
| MySQL 表数据 | 2.5 GB |
| MySQL 索引（含在表数据内） | — |
| RAG 索引 | 29 MB |
| 前端 dist | 2.9 MB |
| 后端 jar | ~50 MB |
| Python venv | 495 MB（可精简到 ~200MB） |
| 日志 + 系统 | ~2 GB |
| **最低** | **10 GB** |
| **推荐** | **20 GB**（留出备份与日志空间） |

## 五、省钱建议：先别急着买

### 5.1 如果只是答辩演示

**不需要买服务器。** 三种免费方案：

| 方案 | 做法 | 优点 |
|---|---|---|
| **本机 + 内网穿透** | 本机跑服务，用 `ngrok` / `cpolar` / `natapp` 映射 5173 | 零成本，性能最好 |
| **本机 + 录屏** | 提前录好演示视频 | 最稳妥，不受网络影响 |
| **云服务器按量付费** | 答辩当天开 4 小时，用完释放 | 几块钱 |

> ⚠️ 内网穿透方案要注意：答辩现场网络可能不稳定。
> **最稳的是提前录屏 + 现场本机演示双备份**。

### 5.2 如果学校要求必须线上可访问

| 场景 | 推荐配置 | 大致价格 |
|---|---|---|
| 仅答辩期间可访问 | 2 核 4G 按量付费 | 几元/天 |
| 长期挂着一个演示站 | 2 核 4G 包月 | 100~200 元/月 |
| 要给别人试用、可能有几个人同时访问 | **4 核 4G** | 200~400 元/月 |

**不建议买 2 核 2G 包年**——省下的钱不够补偿调试时踩的坑（OOM、swap、查询超时）。

### 5.3 如果预算卡在 2C2G，可以这样降配数据

数据量是查询耗时的主要因素。可以把数据集降一档来换取性能：

```bash
# 只保留 2016 全年（约 289 万行，减半）
# 或只保留部分园区（如 6 个园区约 200 万行）
```

这样在 2C2G 上也能跑到 2 秒内，代价是"数据规模 599 万条"这个亮点会缩水。
**不建议**——申报表里把数据规模作为成果，缩水反而损失更大。

## 六、完整部署架构（推荐：4C4G）

```
                    互联网
                       │
              ┌────────▼─────────┐
              │  Nginx :80/:443  │  ~15MB
              │  · 托管 dist/     │
              │  · /api 反向代理   │
              └───┬──────────┬───┘
                  │          │
      ┌───────────▼──┐   ┌───▼──────────┐
      │ Spring Boot  │   │ Python RAG   │
      │ :8080        │   │ :8000        │
      │ 251 MB       │   │ 80 MB        │
      └───────┬──────┘   └──────────────┘
              │                    │
      ┌───────▼────────┐           │ 调用 DeepSeek API（外部）
      │ MySQL 8.4      │           │
      │ :3306          │◀──────────┘ 读统计数据
      │ ~350 MB        │
      └────────────────┘

内存合计 ≈ 700 MB + 系统 200MB ≈ 900 MB
磁盘 ≈ 10 GB（关闭 binlog）
```

**外部依赖**：DeepSeek API（国内可直连，实测握手 0.6s）。
服务器只需能访问 `https://api.deepseek.com`，不需要 GPU。

## 七、一句话回答

> **2 核 2G 内存够（实测约 900MB），但 CPU 会拖慢查询。**
> 建议至少 **2 核 4G**，推荐 **4 核 4G**。
> 如果只是答辩演示，**先别买服务器**——本机 + 内网穿透 + 提前录屏，零成本且性能最好。
