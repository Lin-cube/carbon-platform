# 角色分工与接口契约（v1.0）

> 项目：碳能智控运维平台 ｜ 郑州西亚斯学院 AI+X Vibe Coding 实验班（二期）
> 项目导师：席宏昌 ｜ 周期：7–9 周
> 本文件是**全栈开发**与 **AI+算法（RAG/MCP）** 两个角色的唯一对接依据，双方改动需同步更新本文档版本号。

## 一、角色边界

| | 角色 A：全栈开发（本仓库主要建设者） | 角色 B：AI + 算法 / RAG |
|---|---|---|
| **技术栈** | Vue3 + TypeScript + Vite + ECharts + Three.js（前端）<br>Spring Boot 3 + JDK 21 + MySQL 8（后端） | Python 3.12 + FastAPI + RagFlow + 轻量 LLM |
| **交付模块** | ① 统一能耗数据集构建<br>② 数据导入与治理（五步向导）<br>③ 实时监控与可视化看板（含 3D 园区）<br>④ 查询统计与报表导出<br>⑤ 系统集成、权限与审计留痕 | ① MCP 7 类数据查询工具<br>② RagFlow 建筑能源知识库<br>③ "小E" AI 助手（问答/诊断/报表）<br>④ 分层基线-偏差异常诊断算法 |
| **不负责** | 知识库语料整理、LLM 选型与提示词工程 | 前端页面、数据库表结构、业务 CRUD |

### 关键解耦原则

- 角色 A 产出**统一能耗数据集**与**数据库**，这是角色 B 的输入。
- 角色 B 产出**AI 服务（独立进程）**，角色 A 的后端通过 HTTP 调用，**不直接依赖 Python**。
- 双方以**接口契约**为准并行开发：角色 A 先用 **Mock AI 服务**打通全链路，角色 B 上线后无缝替换。
- **禁止**：角色 B 直接连生产数据库写数据；角色 A 把 AI 逻辑写进 Java 里。

## 二、数据契约：统一能耗数据集

角色 A 产出位置：

```
carbon-platform/data/exports/
├─ unified_energy_dataset.csv.gz     全量（UTF-8，gzip）
├─ unified_energy_dataset.parquet    列式（推荐角色 B 用 pandas 直读）
├─ unified_energy_dataset_sample.csv 5000 行样本（快速上手）
└─ unified_energy_dataset.json       500 条 JSON（MCP 联调样例）
```

字段级定义见 [`docs/data_dictionary.md`](data_dictionary.md)。**对角色 B 最重要的字段**：

| 字段 | 说明 | 角色 B 的用途 |
|---|---|---|
| `building_id` | 建筑唯一编号（如 `Panther_office_Clementina`） | MCP 工具入参 |
| `timestamp` | 小时级时间戳（2016-01-01 ~ 2017-12-31） | 时间范围查询入参 |
| `electricity_kwh` | 电力能耗（实测） | 能耗查询、异常诊断 |
| `hvac_kwh` | 空调系统能耗 = 冷冻水 + 蒸汽 + 热水 | COP 计算、诊断 |
| `cop` | 机组实时 COP（仿真值） | 能效分析问答 |
| `chw_supply_temp_c` / `chw_return_temp_c` | 空调供/回水温度（仿真值） | 诊断规则判据 |
| `air_temperature_c` / `humidity_pct` | 环境温湿度 | 归因分析（"是否因高温导致"） |
| `occupancy_density` | 人员密度（人/100㎡） | 归因分析 |
| `anomaly_flag` / `anomaly_type` / `severity` | 异常标注（算法产出） | 问题诊断工具、召回答辩 |
| `data_quality_flag` / `data_quality_type` | 数据质量缺陷（表计卡死/缺失） | **与能耗异常区分**，避免误报 |
| `equipment_status` | 正常 / 异常 / 离线 | 设备运行状态查询 |

> ⚠️ **数据来源三态**：`实测`（BDG2 原始测量）/ `推算`（物理公式推导，如露点→湿度）/ `仿真`（规则模型生成，如供回水温度、人员密度）。回答用户时必须区分，不得把仿真值表述为实测值——这是申报表第 17 条"风险边界说明"的要求。

### 数据规模参考

| 项 | 值 |
|---|---|
| 建筑数 | 543 栋（18 个园区） |
| 时间范围 | 2016-01-01 00:00 ~ 2017-07-01 11:00（13140 小时） |
| 总行数 | 约 713 万行 |
| 申报表要求 | ≥ 1000 条 → 余量充足 |

## 三、MCP 工具契约（角色 B 实现，角色 A 消费）

申报表明确要求"基于 MCP 协议自研 **7 类**数据查询工具"。角色 B 需实现为 MCP Server，
每个工具的输入/输出必须与下表一致。

### ⭐ 后端已实现这 7 类工具的 REST 形态（角色 B 可直接调用）

**角色 B 无需自己写数据查询 SQL** —— 后端已经把 7 类工具实现为 REST 接口，
入参出参见下表，实测响应时间均 ≤ 1.3 秒（验收指标要求 ≤ 2 秒）。

| # | 工具名 | 已实现的 REST 接口 | 实测响应 |
|---|---|---|---|
| 1 | `query_dimensions` | `GET /api/energy/dimensions?dimension={building\|site\|building_type\|data_grade\|energy_grade\|anomaly_type\|season\|metric\|all}` | 0.044s |
| 2 | `overview_stats` | `POST /api/energy/overview` body: `{startDate,endDate,siteId?,buildingId?}` | 0.153s |
| 3 | `breakdown_stats` | `POST /api/energy/breakdown?groupBy={site\|building_type\|season\|hour\|data_grade}` body: `{startDate,endDate,metric}` | 0.276s |
| 4 | `query_energy` | `POST /api/energy/query` body: `{buildingId?,siteId?,startDate,endDate,granularity:hourly\|daily\|monthly,metric,onlyAnomaly?}` | 0.043~0.117s |
| 5 | `scan_anomalies` | `GET /api/analytics/anomalies/scan?startDate&endDate&buildingId?&siteId?&anomalyType?&severity?&minDuration?&pageNum&pageSize` | 0.110s |
| 6 | `diagnose_issue` | `GET /api/analytics/diagnose?buildingId&startDate&endDate` | 0.074s |
| 7 | `suggest_optimization` | `GET /api/analytics/suggest?buildingId&startDate&endDate` | 0.040s |

另外提供三类统计分析接口（申报表要求的 3 类核心统计分析）：

| 类型 | 接口 | 实测响应 |
|---|---|---|
| ① 时段汇总 | `GET /api/analytics/period-summary?periodType={year\|quarter\|month\|week\|day}&startDate&endDate&siteId?` | 0.880s |
| ② COP 计算 | `GET /api/analytics/cop?buildingId&startDate&endDate` | 0.066s |
| ③ 异常分析 | `GET /api/analytics/anomaly?startDate&endDate&siteId?&buildingId?` | 0.257s |
| 报表导出 | `GET /api/analytics/report/export?startDate&endDate&siteId?` → Excel（5 Sheet） | 2.05s（含文件流） |

**鉴权**：除 `/api/auth/login` 与 `/api/system/health` 外，所有接口需在请求头携带
`Authorization: Bearer <token>`（先调 `POST /api/auth/login` 获取）。

### 统一响应信封（后端 REST 形态）

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { },
  "success": true,
  "timestamp": 1791899556589
}
```

失败时：`{"code": 2001, "message": "建筑不存在", "data": null, "success": false}`

> 状态码见 `com.carbon.platform.common.result.ResultCode`。
> 注意 `data` 中的能耗字段**允许为 null**（园区无该表计时合法缺失），
> 已刻意保留 null 而不过滤，避免调用方误判为"字段不存在"。

### MCP 原生形态的响应信封（角色 B 的 MCP Server 对外暴露时使用）

```json
{
  "ok": true,
  "tool": "query_energy",
  "data": { },
  "meta": {
    "row_count": 168,
    "elapsed_ms": 42,
    "data_source": "实测|推算|仿真|混合",
    "generated_at": "2026-01-01T00:00:00+08:00"
  },
  "error": null
}
```

失败时：`{"ok": false, "data": null, "error": {"code": "BUILDING_NOT_FOUND", "message": "..."}}`

## 四、AI 服务 HTTP 契约（角色 A 后端调用角色 B 服务）

角色 B 需暴露以下 HTTP 端点（FastAPI 默认 `http://127.0.0.1:8000`）：

| 方法 | 路径 | 说明 | 角色 A 调用时机 |
|---|---|---|---|
| `GET` | `/health` | 健康检查 | 系统启动自检、看板"AI 服务状态"指示灯 |
| `POST` | `/ai/chat` | 自然语言问答（RAG + MCP 编排） | "小E"助手对话 |
| `POST` | `/ai/diagnose` | 能耗异常诊断 | 看板点击异常点 → 诊断面板 |
| `POST` | `/ai/report` | 自动化报表生成 | 报表模块"AI 生成初稿" |
| `GET` | `/mcp/tools` | 列出可用 MCP 工具 | 前端展示能力清单 |

### `/ai/chat` 请求 / 响应

```jsonc
// 请求
{
  "session_id": "uuid",
  "question": "A栋教学楼上周三为什么能耗偏高？",
  "context": { "building_id": "Panther_education_Tina", "role": "运维人员" },
  "stream": false
}

// 响应
{
  "ok": true,
  "answer": "……",                    // 自然语言回答
  "citations": [                       // 知识库引用（RAG 溯源，用于准确率评估）
    { "source": "设备运维手册.pdf", "page": 12, "snippet": "……" }
  ],
  "tool_calls": [                      // 本次调用过的 MCP 工具（可解释性）
    { "tool": "scan_anomalies", "args": {"building_id": "..."}, "elapsed_ms": 30 }
  ],
  "data_evidence": { "anomaly_hours": 6, "peak_kwh": 412.5, "vs_baseline_pct": 38.2 },
  "confidence": 0.88,
  "elapsed_ms": 1240
}
```

### 验收指标对接（申报表硬指标）

| 指标 | 目标 | 谁来保证 | 证据产物 |
|---|---|---|---|
| 核心页面平均响应时间 | ≤ 2 秒 | 角色 A | 压测报告 |
| **AI 问答与知识检索可用准确率** | **≥ 85%** | **角色 B** | `docs/eval/qa_testset.csv`（20+ 标准问答）+ 评测报告 |
| **异常识别召回率 / 误报率** | **≥ 90% / ≤ 10%** | **角色 B（算法）**，角色 A 提供标注数据 | `docs/eval/anomaly_eval.csv` |

> **角色 A 的关键配合**：`anomaly_flag` 字段即"算法识别结果"，需要一份**人工标注真值**才能算召回率。
> 标注方案：从 BDG2 原始数据中筛选已确认的表计故障与用能异常时段（含注入式验证样本），
> 形成 `docs/eval/anomaly_ground_truth.csv`。角色 A 负责产出，角色 B 负责评估与调优。

## 六、Mock 优先原则（角色 A 落地要求）

在角色 B 的 AI 服务就绪前，角色 A 必须在后端实现 `AiServiceClient` 的 **Mock 实现**：

```java
public interface AiServiceClient {
    ChatResponse chat(ChatRequest req);
    DiagnoseResponse diagnose(DiagnoseRequest req);
    ReportResponse generateReport(ReportRequest req);
}
// MockAiServiceClient  -> 返回契约定义的假数据，供前端全链路开发
// HttpAiServiceClient  -> 真实调用角色 B 的 FastAPI 服务
```

通过配置 `carbon.ai.mode=mock|http` 切换。**这样角色 A 全程不被角色 B 阻塞**，
角色 B 上线后只需改一行配置即可完成对接。
